## 0. 先看结论（一页纸）

### 0.1 六个方面的体检结果

> **先把"实测"说到位（重要）**：这次评审时，本机只有 3 条长期记忆、5 条临时原文缓存，而且 4 个工作区全部停用——**这个样本量根本测不了"找得准不准"**。下表每个格子里标了证据来源，只有三种：
> - **真实观察**：本机存的数据、插件运行时读到的快照、逐个测试文件实跑——只能证明"系统在跑 / 这些毛病真的存在"，不能证明"它记得好"；
> - **合成集复算**：在 `frozen-v2` 这个固定评估集上（215 条人造记忆 + 20 条临时缓存，连语义索引数据都是人造的）重新跑一遍算出来的数——只说明"机制在受控条件下表现如何"，**不是你真实记忆上的效果**；
> - **读代码确认**：翻代码、文档、测试得出的事实。
>
> **打分标准**：设计分看机制是否完整、工程是否扎实；证据一栏不把"设计好"混成"实测好"。**A/B/C**：A = 机制完整，而且有评估或实测支撑；B = 机制完整，但有明确缺口或还没验证；C = 明显不足。

### 0.3 这些建议和"现在已有的功能"是什么关系

- **不是重写**：绝大多数建议不改存储主格式，也不动查找的主流程。
- **大约一半是"把入口接上"**：编辑、反馈、导出、趋势要用的数据（证据记录、操作记录、自动带入日志、详情）**其实都已经有了**，缺的是后台接口、按钮和一致性处理；另一半需要新的数据或新的表（导入、指标汇总、按"说的对象"筛、关系候选通道），文中逐项标了。
- **"不真正删除"要限定范围**：DESIGN §9.9 说的不删除，指的是长期记忆、人格设定这类长期记录；临时原文缓存是会话日志的副本，待整理队列是临时队列，清理它们本来就是设计的一部分。**R16 如果真要删"还没整理过的临时缓存"，必须先确认原文还能从会话日志取回来**，否则就保留并告警（详见 R16）。
- **分清四类**：新增能力 / 改造已有能力 / 把 DESIGN V2 已经规划的东西提前 / 只改默认值（第 6 节逐项标注）。

## 2. 它现在是个什么东西

### 2.1 它想解决什么问题

给 DSH 加一个**带来源、带证据的长期事实库**，而不是"聊天记录搜索"：

- **写**：每回合的原文先放进临时原文缓存（不调用模型，几秒内就能被查到），后台攒成一批再整理成长期记忆里的"事实 / 经验 / 话题摘要"；用户明确说"记住"时，可以走 `memory_remember` 先放进待确认区，确认后转正。
- **读**：每轮对话一开始（第 1 步）就把相关的记忆找出来、自动带进上下文；另外还有每轮都带的经验条目、开场摘要、用户画像、人格设定这几层。
- **管**：每条记忆都带来源（哪个工作区、哪次会话、什么时候）、证据记录（"这条对 / 这条不对"）、有效期、被取代或存在争议的状态；不真正删除，可以追查。
- **控**：一个 7 页签的记忆控制台（总览 / 记忆 / 检索 / 设置 / 画像 / 人格设定 / 操作记录），入口在主侧栏。

它和同类插件不一样的地方，DESIGN §12 写得很清楚：**用证据决定记忆的去留、拿代码里的事实做核对、来源分得干净、所有项目共用一个池子、先存原文再整理的两档速度、人格设定可以自己改**。这些在同类插件里确实少见。

### 2.2 现有能力全貌（按环节）

| 环节 | 已经能做到的 | 状态 |
|---|---|---|
| 写入 | 临时原文缓存（工具输出只留摘要、失败输出单独保留、代码块折叠、思考过程只有手动查找才看得到、敏感内容初筛默认关闭）；每 6 轮或者空闲 5 分钟触发一次整理；待整理队列重复执行也不会重复写入、失败会重试；主动记忆先放待确认区、确认后转正；重复内容合并（按规范化文本、按说的对象、并发写入、待确认区复用）；新旧关系处理（印证、取代、标争议、判无关 + 一层保护措施）；三层防外部内容冒充指令的防护 | 稳定 |
| 读取与自动带入 | 用户画像（只有一个文件入口 + 轮询 + 系统提示里的一段，排在 420）；每轮自动带入（第 1 步、每轮都带的经验条目、开场摘要、按会话算额度、上下文紧张时自己收敛、对话被压缩后把记忆补回来、本次会话已经带过的不重复带）；带入前核对（这条记忆还在不在、内容对不对得上、代码文件最后修改时间变没变）；查找工具（按关键词、按时间、按会话过程复盘、按编号展开整条原文）；忘记（停用 / 彻底隐藏 / 连带清掉临时缓存）；人格设定（自己改、有版本、能回滚、每天有限额、按 agent 决定装不装） | 稳定 |
| 查找 | 关键词匹配（中文按 2–3 个字切词，另外按标识符再切一次）；可选的语义检索（自动分段 + 检查向量维度对不对 + 换模型时重新生成语义索引数据）；两路结果按名次融合；绝对相关性门槛（两路结果一致时一条线、只有一路结果时一条线、纯关键词匹配时再一条线）；时间越久越降权 + 证据系数 + 所属工作区 + 说的对象加权 | 稳定；默认大多走纯关键词匹配 |
| 从产生到消失 | 证据明细和随时间降权；进行中事项的有效期和续期；`validUntil` 和待办；取代、争议、被说服、假设演进；负分连续 14 天停用；每 30 分钟清扫一次 | 稳定；缺恢复和容量管理 |

### 2.3 哪些能放心用、哪些还没底

- **稳定核心（可以日常用）**：临时缓存和长期记忆的写入、混合查找、自动带入的规矩、隐私硬过滤、四个工具、7 页签控制台、人格设定、操作记录。
- **已经做完、但用的人少 / 看不见**：用户画像（唯一入口是手工改文件）、开场摘要（默认关）、每轮都带的经验条目、会话过程复盘、人格设定的提议。
- **实验或受限**：语义检索（默认没配，实际走纯关键词匹配）、新旧关系判断（`frozen-v2` 里关系样本很少）、跨语言、非 git 目录的归属、子代理场景。
- **已规划、还没做（DESIGN V2/V3）**：画像晋升（从记忆生成画像候选）、记忆纠错（直接改正文）、敏感标记改标入口、被取代条目的平反、等待删除记录的重放、话题层独立成层、工具使用防护、按"说的对象"设硬门槛、按主题一键忘掉、同类经历合并；以及 NEXT_STEPS 里的 **N2：管理接口的自动测试矩阵 / N3：不重启重新加载的测试矩阵**（目前只有手动检查脚本，不重启重新加载还没有自动断言）。
- **明确不做（DESIGN §9）**：用模型重排、引入专门的语义索引数据库（也就是常说的向量数据库）、定时主动提醒、真正删除、抢对话压缩的职责、人格设定分档、通用进程管理等。

> 这意味着本文的建议**大部分不是"新机制"**，而是把 V2 已经规划、或者底层数据已经有了的东西，挪到"用户能操作"的位置。

### 2.4 它和 DSH 自带的功能怎么分工

| 能力 | DSH 自带 | 本插件 | 关系 |
|---|---|---|---|
| 行为规矩 | `AGENTS.md` + 按项目逐层往上找，额度 64KB，第一轮作为基准消息 | 用户画像放"关于用户的稳定事实"；人格设定放性格口吻 | 不重复；README/DESIGN 已经写清边界 |
| 会话历史 | 会话日志 + `sessionQuery` + 对话压缩 + 用量统计 | 临时缓存是短时副本 + 长期记忆是整理后的事实；展开原文走 `sessionQuery` | 互补；插件不自己写会话日志 |
| 会话搜索 | 官方 `session-search` 插件（当前配置里没启用） | 会话过程复盘 + 查找时展开原文片段 | 场景有重叠，但定位不同：一个搜原文，一个想事实 |
| 提醒、定时 | 自带的 `schedule_*` 工具 | 没有闹钟；只有对话开场时自动带入 | 不重复；"提醒我"应该交给定时任务，插件只记待办和截止时间 |
| 任务、协作 | agent teams（多智能体协作功能）+ 共享任务板 | 全局记忆池（按内容自动共享） | 没有"任务记忆"的概念；建议保持边界 |
| 设置、页面 | `configForms` + 主侧栏插槽 | 7 页签控制台 | 已经正确接上了 |

**结论**：插件没有抢 DSH 的职责，边界是干净的。它缺的不是"更多自带能力"，而是把自己那一层的产品面做完整。

### 2.5 先说好的：五件不该为了改而改坏的东西

1. **用证据决定记忆的去留**：印证和质疑两本账、随时间降权、进行中事项的有效期、取代 / 争议 / 被说服 / 假设演进——这是插件真正的差异点，不建议为了"简单"而削弱。
2. **拿代码里的事实做核对**：记住代码里的位置 + 存在性和内容两级核对 + `lastVerifiedAt` 摘掉"待核实"的帽子 + 渲染时提醒"以当前代码为准"——同类里少见，是写代码场景的护城河。
3. **来源分得干净**：`user / assistant / code / tool / quote` 五类来源分开渲染，转贴的资料不能顶用户的名义——这是"可信记忆"的地基。
4. **人格设定分层**：人格、记忆、行为规矩、角色四层分开；自己改的时候带理由、限额、版本、回滚——定位独特，机制克制，不建议动。
5. **工程质量**：307 项测试、六类接口自动检查、固定评估集、对话从头到尾的测试、发布矩阵、出错时的备用方案 + 操作记录纪律——在个人插件里属于少见水平，是这个项目最被低估的资产。

> 这五件事决定了项目的"下限"；下面的建议只动"上限"，不动这些下限。

## 3. 从六个方面看它实不实用（附证据）

### 3.1 把对话记下来：A−

**做得好的**：每轮对话一结束，内容就自动进了临时原文缓存（每次对话后先把原文存一份的地方），用户不用做任何操作；后台整理有防重复的标记、一批一批的处理记录、崩溃后的核对、彻底失败后等一会儿再试；用户主动说"记住"时，有"先放待确认区、再确认"两档；隐私初筛在存到磁盘时做（默认已关，见 R4）；临时原文缓存出问题不影响聊天。还有一个常被误解的点：**不怎么活跃的用户，第一条长期记忆并不需要攒满 6 轮**——每轮结束都会重置一个 5 分钟的空闲计时器，到点只要还有待处理的内容就整理（`lib/extract.js:44-68`）。所以"当天第一轮结束后大约 5 分钟"就能产出第一条长期记忆（前提是进程还活着）。

**问题（按证据的强弱排）**：

1. **一个回合太长，整条被丢掉（证据很硬）**。本机 5 条临时原文缓存里，有 3 条是因为单个回合超过 `extractMaxInputChars=65536` **个字符**（是字符不是字节；中文下 65,536 字符和 64KiB 差大约 3 倍）被标成 `deadLettered`（彻底失败、等着删除），操作记录里留下 3 条 `extract-oversized-turn`，之后到期被真正删除（`lib/extract.js:572-592`）。根因是 `renderOriginal` 把工具输出的**全文**拼进回合原文（`lib/hotbuffer.js:31-43`），写代码时"读大文件、看很长的构建日志"最容易撞上。这个上限**不在记忆页可以改的范围内**，普通用户连"把它调大"的入口都没有。这些内容只留在会话日志里，记忆池永远收不到。真实数据里，这个记录窗口的 5 个回合有 3 个就是这样丢掉的（60%）。
2. **记录通道曾经静默断掉（v1.16 修了但还没发布）**：本机会话库 34 个（排除 2 个已收起的旧会话后是 32 个）/ 70 个回合结束事件（turn/end），真正进到临时原文缓存的只有 5 个（按 68 这个统计标准是 7.4%）；从启动（07:48Z）到第一条临时原文缓存（13:22Z）之间有 15 个回合（12 个子代理 + 3 个主会话）一条记录都没有，当时 `/memory/api` 只返回 1 个工作区、没有健康状态；23:07 之后才恢复成 4 个工作区 + `health.state=ready`。v1.16 里"回合记录出问题会退到备用方案并自己恢复 + 工作区三个来源合并"修的就是这条，但**现在仍然只是没有发布的 HEAD**。这也说明 R0（收尾发布）不是走形式。
3. **关掉后台整理，临时原文缓存会无限增长，而且永远参与自动带入**。`extractEnabled=false` 时只写临时原文缓存、不登记待整理队列，而清扫（`sweep`）对"没整理过、也不是彻底失败"的临时原文缓存**永不过期**（`lib/hotbuffer.js:118-133`）。用户以为只是"省几次模型调用"，实际上是历史原文永远留在可供查找的池子里，磁盘和自动带入的噪声持续增长。这是设置含义上的陷阱，不能当成普通的"少个功能"来理解。
4. **重复说一遍，不等于这条记忆更可信**。去重命中时只写一条 `extract-dedupe` 操作记录就 `continue`，**不记证据、不续期**（`lib/extract.js:736-744`）；用户主动要求记住时，命中已经生效的同一条内容，也只回一句"没有重复写入"（`lib/tools.js:344`）。于是"用户反复确认过的事实"，证据得分仍然可能是 0，照样随时间降权、退出候选，甚至被停用——用户看到的就是"我明明说过很多次"。
5. **敏感词筛查会误伤（证据很硬）**：本机 5/5 条临时原文缓存全部被标成 `sensitive`（敏感）。逐条核对命中的词（连思考过程一起看）后确认：**emo 5/5**（全部是 "memory" 里面的一段）、**NDA 4/5**（"standard/descendant" 这类词里的一段）、**诊断 3/5**（"诊断卡/诊断工具"这类技术词）；`prescreenSensitive` 用的是 `lower.includes(keyword)` 这种"包含就算命中"的比对（`lib/text.js`）。因为 `sensitiveNoCross` 默认是开的，这些技术记忆会失去跨工作区自动带入的资格。这不是某一处的小毛病，而是"按字符串包含来匹配 + 中文一词多义 + 初筛连思考内容一起看"共同造成的一类误报。**2026-11-08 定：自动敏感标记默认关掉**（本机单人使用，不需要这层隔离；见 R4 / §10 第 3 条），误报问题随之消失。
6. **用户画像只能手工编辑**：唯一的数据来源是 `profileFile` 指向的那个 md 文件；控制台的画像页可以直接改它（`profileSave`），但**没有自动生成、也没有从别处晋升上来的通道**——后台整理只产出人格设定的修改提议，没有画像候选。实际在本机，`profile` 没有配置、画像字符 0、`~/.dsh/SOUL.md` 不存在——这两层"每轮都带进对话"的价值完全没发挥出来。
7. **默认设置下没有语义能力**：本机 `semanticSearch` 没有配置，3 条记忆里 0 条有语义索引（语义索引覆盖 0/3），实际走的是纯关键词匹配；README 也承认跨语言、换一种说法再问，找得会差一些。纯关键词匹配这一档的自动带入质量见 §3.2（不该命中的查询 6/13）。
8. **"为什么没记住"没法解释**：`confidence` ≤0.5 而被丢掉的数量被直接扔掉、不写进操作记录（`lib/extract.js:653`）；`llm` 服务没启动、模型选择解析失败、等着再试的时候失败，都只写一条 `logger.info`（默认日志级别下看不到）；第一次启动的引导只写一行日志，`onboardedAt` **没有任何地方会读**（`lib/index.js:219-222`、`lib/api.js` 里没有这一项）。用户只能看到"还有 N 条没整理"，判断不出是模型挂了、模型选错了，还是内容被过滤了。

> 判断：记录这一环，"机制可靠性"很高，但"长内容进不进得来""重复一遍算不算数""人能不能感觉到"是三个真实短板；而这条链路曾经整体静默断掉，说明**把版本发出去、让人看得见，比再加一套机制更重要**。

### 3.2 查找：B（没配语义检索时是 B−）

> **关于这些数字的说明**：本节 0.973 / 6/13 / 前 5 条里相关条目的比例 0.22 这些数字，来自 `frozen-v2` 这个人为构造的固定评估集，是离线重算出来的结果，**不是你本机真实的数据**；本机评审当时真实自动带入 0 次、只有 3 条长期记忆，测不出真实的查找质量。真实池子过去的统计标准见 README（2026-09，前 5 条命中率≈0.73–0.75，池子的快照不一样）。

**做得好的**：关键词匹配 + 语义检索 + 名次融合，再加一道绝对的相关性门槛；按时间、证据、所属工作区、说的是哪个对象等多个因素排序；自动带入的额度是 300ms / 1500 字符；压力大时会自动调整；对话被压缩后会把记忆补回来；带进对话之前会先核验；检索试验台（控制台里用来试查的页面）能直接看到两路各自的得分和门槛的判断依据——这种能看清缘由的程度，同类产品里少见。

**问题（多数来自专门针对查找的重新计算，统计标准见附录 C）**：

1. **默认设置（纯关键词匹配）到底什么水平，没人量过，而且明显更差**。`frozen-v2` 重算：两路都开时，不该命中的查询 13 条里有 2 条被带进来，平均每次带 0.77 条；**只用关键词匹配时，不该命中的查询 6/13，平均 2.15 条**，连"天气/股市"这种闲聊也各带进 4 条。把 `bm25OnlyMin` 从 2 提到 10，不该命中的又回到 2/13，前 1 条命中率反而升到 1.000——这个提升**只改一个默认值**就能拿到（见 R18）。而绝大多数用户没有配语义检索。
2. **`frozen-v2` 那个亮眼的总体数字，主要是关键词匹配的成绩，不是"两路合用"的成绩**：把语义那一路去掉之后，前 1 条命中率/前 5 条命中率/答案平均排名质量仍然是 0.973/1.000/0.980；语义那一路对总体数字只贡献了 37 条查询里的 1 条。前 1 条命中率/前 5 条命中率=1.0 不能当成真实质量的预期。
3. **真正的问题不是"没找到"，而是"找错了对象"**：查询里点名的那个对象（omega/私有项目）不在池里时，系统仍会拿"额度/数据库"这类词去凑，匹配到**别的对象**的记忆，还把 5 条额度填满；容易误判的查询 4 条里有 2 条就是这么来的（2/4）。门槛只看匹配强度（关键词得分和语义相似度得分），**没有"说的是不是同一个对象"这一条判断**（`entity` 只给 ×1.1 的加分）。
4. **"该命中的都带满 5 条"不是优点**：`frozen-v2` 里该命中的查询，带进来的 5 条中有 4 条是别的项目的同款条目（前 5 条里相关条目的比例约 0.2；`frozen-v1` 按同一统计标准只有 1.38 条）。评估只看了有没有找到，没看准不准、也没看搞错对象的比例，于是"带满"被误当成好消息。
5. **查询只用当前这一轮用户说的话**（`lib/inject.js:435-441`），不拼接历史、不改写、不解析时间："继续""那个呢"这类话命中 0；"上周说的那个端口是多少"在纯关键词匹配那一档带进了 5 条别的项目的端口。`turns.recentTexts` 其实已经缓存了近几轮文本（`lib/turns.js:222-228`），但只用来判断说的是哪个对象，没有用来补充查询词。
6. **条数额度和字符额度互相打架**：默认 `injectMaxItems=5` 乘 `excerptChars=300` 装不进 `injectMaxChars=1500`；片段都用满时实际只带 4 条（要带 5 条，平均每条得 ≤271 字符），而且超了是"整条丢掉"而不是截短——排第 1 的长条目会把后面 3 条短的挤掉（见 R20）。
7. **300ms 不是到点就断的硬限制，是事后才检查**：语义检索一旦慢（README 甚至建议 `timeoutMs=600`），这一轮的自动带入会被整个砍掉，而不是"退到纯关键词匹配继续带"（见 R24）。
8. **D3 的"跨层去重"只是名义上做了**：触发条件要求同一次会话，并且长期记忆的原文是临时原文缓存里的逐字子串；只有 1–2 条手工写的单元测试（`test/pipeline.test.mjs:341` 附近），`frozen-v2` 里一对都没有（而且长期记忆和临时原文缓存的 `sessionId` 不一样），真实使用中能命中的概率存疑。同一件事在"临时原文缓存的全文"和"长期记忆的一句话"两处重复出现这条路还开着（见 R21）。
9. **关系候选的命中率 0.375，不是"门槛值调一调"能解决的**：有争议的那一端（`m_alpha_db_alt`）在按事实查找时关键词匹配排第 42/204，前 8 名永远进不去；该取代的那一端则被 `supersededFactor=0.3` 挤出前 8。D2b 只调门槛值治不了，得先改候选的选法（见 R23）。
10. **评估的统计标准有缺口**：没有衡量"准不准"和"搞错对象"的指标，也没有"追问""跨语言""标识符""代码位置核对""摘要""每轮都带"这些类别；评估工具只管 `search.search` 这一处，额度、去重、核验、呈现只在"用假的上下文对象搭起来"的流程测试里。
11. **`openingDigest` 默认是关的**：这是 v1.13 为了减少噪声做的决定（这个决定是对的），但也意味着"主动给你提一句"这个能力默认没有；用户真想用时会发现，设置页里改不到（见 P7）。

> 判断：查找的**机制**（两路 + 名次融合 + 相关性门槛 + 核验）是好的；问题集中在"默认值""说的是不是同一个对象""额度之间怎么配合""评估的统计标准"——这些都能在不上模型重排、不引入图数据库的前提下修。

### 3.2.1 三个补充事实（避免看错文档）

- **随时间降权，对多数长期记忆并不生效**：`temporal='pattern'`（按"长期有效"处理的时间类型）或者 `importance≥8`（重要性 ≥8）的条目，权重恒为 1.0（`lib/rank.js:41-52`），而后台整理用的提示词默认把知识、偏好、约定都判成 pattern（`lib/extract.js:314`）——这是设计上的选择，不是 bug，但"记忆会随时间被降权"对多数条目并不成立。
- **被找出来一次，有效期就续一次**：每次被带进对话的 `state` 类记忆（进行中的事项）都会续期（`lib/inject.js:636-660`），"经常被带进对话"于是变成"永不过期"；只有有争议的那一对是例外。这和"没人用的才慢慢降权"这个目标是有矛盾的。
- **纯中文的代码位置核对会假通过**：内容里没有拉丁字母或数字时，`contentVerify` 直接返回 `'pass'` 并写 `lastVerifiedAt`（`lib/inject.js:284-285,350-352`）——"根本没核验，却留下了已核验的痕迹"，会让"待核实"的标记提前摘掉。

### 3.3 信任与可控性：C+

这是全文最重要的一节。

**做得好的**：7 个页签的控制台；记忆的列表、搜索、筛选、详情；待确认区里的确认和拒绝；操作记录表；人格设定的编辑、历史、回滚；设置页能搜索、能诊断、能选工作区；检索试验台；自动带入日志（只放在内存里、最多 60 条，不记正文也不记查询，隐私上很克制）。

**问题（都可直接验证）**：

- **记忆改不了**：没有后台接口，也没有页面。`lib/api.js` 里只有 `list`/`detail`/`search`/`confirm`/`reject`/`audit`/`soul`/`profile`/`embed` 这些动作（`lib/api.js:836-858`）；`confirm/reject` 也只对 `status==='staged'`（待确认）的条目生效（`lib/api.js:528-567`）。
- **对已经生效的记忆，不能印证也不能质疑**：证据记录 `evidence[]` 目前只由后台整理时的关系判断和"待确认区里的确认"写入；用户看到一条很准的记忆，没有"对"的按钮；看到一条错的，也没有"错"的按钮。
- **在控制台里不能停用、恢复或彻底隐藏**：想停用，只能让模型去调 `memory_forget` 工具（`lib/tools.js:559-573`）；已停用的条目在查找时还看得见，但页面上没有"恢复"。
- **不能导出、备份、导入**：`/memory/api` 没有 export/import；代码仓库里只有发布用的压缩包和升级后的快速自检（那是内部的工程资产，不是给用户备份用的）。
- **没有"这条记忆是从哪来的"跳转**：详情页有信息表和证据时间线，但不能一键回到来源会话、也不能展开原文（`memory_recall` 做得到，控制台做不到）。
- **"为什么这次带进来了、为什么没带"之后就没有下文了**：总览能看到最近带进对话的记录和跳过的原因（这点很好），但看不到"这条带进去之后有没有派上用场"。
- **把来源记错的隐患**：`memory_remember` 把模型自己写进来、还在待确认区的条目也标成 `source:'user'`（`lib/tools.js:351`），带进对话时就会说成"你之前说过"；用户看到自己没说过的话被当成自己的原话，这是信任上的硬伤（修起来成本很低，见 R13）。
- **模型看得到记忆，却拿不到引用编号**：带进对话的那一行不带记忆编号（`lib/inject.js:194`），模型没法对"刚看到的事实"精确引用、忘记或纠正，只能再查一次。
- **编辑画像时可能悄悄丢数据**：外部画像文件超过 20,000 字符时，页面拿到的只有前 20,000 字符，并标上 `truncated`；用户随便改一点再保存，写回去的就是被截断的那一版，尾部内容永久丢失（`profileSave` 只拦住 >20,000 的保存，认不出源文件已经被截断）。

> 判断：**底层数据是齐的，缺的是给人用的操作入口。** 这是投入产出比最高的一块。

### 3.4 记忆从产生到消失的全过程与日常打理：B

**做得好的**：证据明细、随时间慢慢降权、按 S 形曲线换算权重；`state` 类记忆（进行中的事项）的有效期分档 + 被找出来就续期 + 宽限期；validUntil/todo；取代、争议、被说服；证据总分 ≤−2 连续 14 天停用；每 30 分钟清扫一次；不做真正删除，都有操作记录。

**问题**：

1. **只会变多，没有"体检"视图**：记忆、临时原文缓存、待整理队列的**总条数**有，工作区分布也有计数（记忆页的分类统计），但没有磁盘占用、新旧分布、变化趋势；没有重复检测（写入时有完全相同的去重，但历史上近似重复的还在）；也没有"很久没核验过的、靠代码位置撑着的记忆"这类巡检。
2. **没有恢复和清理的工具**：停用只能通过模型调工具；彻底失败、等着删除的记录在总览里只是一个数字，不能查看也不能重放（关键指标里有失败数）；临时原文缓存里的失败记录 48 小时后被真正删除，用户完全感觉不到。更隐蔽的是：待整理队列里 `skipped` / `dead` 的行**永远不清**（`lib/outbox.js:80-82` 只删已经做完的），用久了会攒下一批只增不减的"垃圾行"。
3. **旧的结论可能永远盖不掉**：写关系时的保护措施只认 `temporal` 相等，不相等就直接拒写（`lib/relation.js:52`）。如果模型这次把同一件事判成 `state`（进行中）、上次判成 `pattern`（长期有效），新记录就没法取代旧条目；而关系候选默认只取**纯关键词匹配的前 8 名**（`lib/extract.js:607-615`；配了语义检索才是两路合用），前 8 名之外的老条目永远等不到"被取代"。表现出来就是新旧两条同时生效、同时被带进对话。
4. **没有"改敏感标记"的入口**：标错了（如 3.1 第 5 条）现在只能把整条记忆忘记，不能只改那个标记。
5. **容量上限只是"照内存规模设计的"**：到几万条以后需要专门的索引（DESIGN 里说过了），但用户这一侧没有任何"该清理了"的提示。
6. **几个不大但真实的小毛病**：`lessons` 不受 `extractMaxFacts` 限制（`lib/extract.js:643-646`）；写关系时缺少 `created.id === target.id` 这种"指向自己"的防护；`reconcile` 会清掉 `nextRetryAt`，重启一次就绕过了"等一会儿再试"（模型配错的时候，5 次失败重来可能在 5 次重启之内就烧完）；"原文拿不到"和"回合太大"共用一个跳过分支，容易把原因判断错（`lib/extract.js:562-591`）。

> 判断：记忆从产生到消失的规则，是同类里做得最细的；缺的是"让它长期保持干净"的给用户的工具。

### 3.5 多人与多种场景下的适配：C

**现状证据**：评审期间用本机 `/memory/api` 实际测过：4 个已注册的工作区**全部**在 `disabledWorkspaces` 里（启用 0/4）；**截至 2026-11-08 00:50 的实时快照**是自动带入 0 次、跳过 17 次，原因只有 `subagent`（9 次）、`workspace-disabled`（3 次）、`no-query`（5 次）；现在这 3 条长期记忆全部来自同一个子代理会话（同一批写入、重要性 5、没有语义索引、没有证据记录，来源分别是 code/tool/assistant 各 1 条、**user 0 条**）；5 条临时原文缓存里有 4 条来自子代理；主会话里 24 个 dsh-memory 回合，产出 0 条长期记忆。也就是说：**真实数据里，子代理才是写入主力，但插件没有子代理来源标记，也没有子代理写入策略**（`injectToSubagents` 只管要不要自动带入，不管写入）。

**问题**：

1. 子代理会话写进来的长期记忆，和主会话的记忆混在同一个池子里，既没有来源标记，也没有可信度区分；多人协作时，可能把子代理的中间结论当成"用户说过的话"带进对话（带进对话时的说法由 `source` 决定，和是哪个助手写的无关）。
2. **团队和任务记忆没有定义**：记忆池是全局的，但"某个任务、某次团队协作的上下文"既没有范围的概念，也没有和 DSH 任务板、会话之间边界的说明。
3. 不用 git、又在同一个目录里跑多个任务时，"这条记忆算谁的"很弱（DESIGN 里已经承认这点，V2 对"说的是哪个对象"设了硬性要求）。
4. 停用工作区是"整个停掉"，管得太粗；没有"只在这个会话里先别记"。

> 判断：一个人、一个工作区的场景够用；用上 agent teams、多个项目并行时，写入怎么管、来源怎么标，就会变成真问题。

### 3.6 能不能看清它在干什么，以及成本：B−

**做得好的**：总览一屏就能回答"记忆在工作吗、存了多少、最近带进了什么、为什么没带进来"；七项健康检查；检索试验台；语义检索失败时退到备用方案的记录；启动时的 health 状态（v1.16）把"悄悄不工作的状态"摆到了页面上。

**问题**：

1. **自动带入日志不存到磁盘**：`lib/injectionlog.js` 里写得很清楚——"只在进程内的环形缓冲里，不存磁盘"，上限 60 条，**重启、或者保存设置后不重启就重新加载，都会清零**；`counts` 也只是本次运行的累计。用户没法回看昨天或上周。
2. **没有按时间的变化**：没有"最近 7 天带进对话的次数、字符数、命中率、跳过原因分布"这样的趋势。
3. **没有模型用量和成本的账**：带进对话的字符数有，但没换算成模型用量；后台整理调用模型的次数只散落在操作记录里；语义检索的延迟和失败有退到备用方案的记录，但页面上没有汇总。
4. **没有用户的反馈**：回答不了"记忆到底有没有帮上忙"。
5. **"为什么没带进来"仍然是很粗的原因**：自动带入日志把"没找到 / 全被相关性门槛拦下 / 额度不够丢掉 / 超过会话上限丢掉 / 已经带过了 / 太久没用被停用"混成一个 `no-hits`；检索试验台里被门槛拒绝的也看不到。用户定位不到是哪一环出的问题。
6. **来源追不全**：README 说每条记忆都带"来自哪个会话、什么时间"，但 `detail` 只返回记忆表里的那些列，不含 `sessionId`/`sourceRange`；临时原文缓存里的 `hb_…` 条目在控制台翻不到，详情页也没法从一条记忆跳到它的来源会话。
7. **控制台的刷新和反馈对不上**：页头的"刷新"只重新拉一部分面板（画像和人格设定没有 `refreshKey`）；设置保存后没有"正在重新加载 / 已生效 / 失败"的状态；搜一个"存在但不能改"的设置项，只提示"没有匹配"；Browse 里确认或拒绝之后，总览的关键指标不跟着刷新。这些都会让用户误判成"是不是没保存""是不是根本没这个功能"。
8. **漏接的后台接口与取证**：`injections`/`search`/`stats` 这三个 DSH 本体提供的动作，客户端根本没接上（按所有者做的全池语义检索其实已经就绪，可是 Browse 里只做了字符串包含过滤）；操作记录页面只取 200 条（最多能存 2000 条），没有服务端筛选，也没有分页；`inject-error` 没有多语言（i18n）文案；`health.warnings` 根本不显示；"手动触发""看日志"这类提示指向的入口并不存在。更糟的是**启动失败时 `/memory/api` 可能整条都访问不到**（旧路由注销了，新路由又没注册），恰恰在最需要诊断的时候看不到诊断信息。
9. **没有"这个回答用了哪几条记忆"**：用户在聊天里看不到"这次回答用到了哪几条记忆"（自动带入日志里有命中编号，但只在控制台里，而且只有内存中的 60 条）。这是两件事："趋势能看清"和"单独一轮能追查"：前者按天汇总就够了，后者需要按轮保留命中编号（存在本地、只留编号、留 7 天、不记正文和查询）——文档里不要把前者当成后者。
10. **操作记录不好读**：23 条操作记录里有 17 条是 `soul-inject-ready`，真正有价值的事件被淹掉了；也没有按类型、按严重程度聚成一份"需要留意"的摘要（设置页有诊断卡，总览还可以再往前走一步）。

> 判断：单轮的诊断已经很强；缺的是"跨天、能对比、能据此做事"的观察视角。

### 3.7 模型这一侧的体验（工具用起来怎么样）：B

这一维不直接决定"功能有没有"，但决定"模型会不会用、用得好不好"。把四个工具逐项看过一遍之后（详见 `.scratch/review/03-tools.md`）：

- **优点**：报错的话大多能照着做（时间格式错会给正确格式、工作区停用会告诉你去哪儿启用、密钥被拒会给改写建议、被判成冒充指令而拒收时会给你换一条路）；`source`/`entity`/`temporal`/`kind` 这几项各自是什么意思，写得很清楚；安全保护措施（密钥、冒充指令、越权）在工具这一层有落实。
- **缺点 1（信任）**：`memory_remember` 一律写 `source:'user'`，自动放进待确认区的事实，之后会被说成"你之前说过"。
- **缺点 2（额度）**：`memory_recall` 默认 10 条，超了不吭声直接截断，最坏大约 32.6k 字符；按编号展开最坏大约 49k；`memory_forget` 附带的"相关记忆"没有上限——反倒是自动带入那一侧有 1500/6000 字符的硬额度，两边不对称。
- **缺点 3（流程走不完）**：带进对话的那一行没有编号；查找结果不说"下一步可以做什么"；模型不能确认也不能拒绝待确认区里的条目；用户以为"助手会帮我整理待确认的"，这个预期落空了。
- **缺点 4（不容易被发现）**：系统提示里没有一句总述说明"有记忆工具、什么时候该写"，全都压在工具自己的描述里（四个工具的定义实测 1,992 字符），而且参数规则和参数描述有重复；触发场景只写了"之前/上次/还记得吗"，漏掉了"继续上次的任务/引用历史的决定/要求引用原话"这些很常见的场景。
- **缺点 5（界限）**：人格设定和记忆、和 AGENTS.md 之间，写哪个的界限只写在 README/DESIGN 里，模型这一侧缺一句"偏好和事实写进记忆，性格和口吻写进人格设定"。

> 判断：这些工具"安全，但面偏窄"；R13 那个小改动能拿掉最要命的信任和额度两个问题，R11 的 `memory_update` 补上"纠正"的能力。

### 3.8 检查结论

- **工程成熟度**：A−（测试、自动检查、出问题退到备用方案、文档上的自我要求，在个人做的插件里属于顶级）。
- **产品成熟度**：C+（给人操作的入口、默认体验、长期能不能看清）。
- **建议的方向调整**：从"把记忆的机制做对"，转到"让人用得上、敢相信、能纠正、看得见价值"。下面第 4–5 节给出具体清单。

### 5.1 P0：信任与默认质量补丁（建议 0.6.6）

> 本节按"主题"组织：R1a/R4/R13/R18 是 P0；R1b/R1c/R2a/R2b/R3 是同一主题下的 P1/P2，放在一起便于阅读，排期以 §5.0 表和 §9.1 为准。

#### R1a/R1b/R1c 记忆管理的操作入口（分成三步）

**问题**：用户能看到记忆，但改不动、评不了、恢复不了。证据记录这套东西目前几乎只有模型单向输入（整理时判断关系）和一次性确认待确认区。

**现状对照**：

- 已有：记忆列表 / 搜索 / 详情（`list/detail`）、待确认区的确认 / 拒绝（`confirm/reject`）、操作记录、控制台的试查页面、`forget` 工具、`memory_remember` 工具。
- 缺失：改正文 / 内容项、用户说"这条对 / 这条不对"、停用 / 恢复、彻底隐藏（页面上）、改敏感标记、操作历史。

**方案（按落地顺序分开做）**：

1. **R1a（P0，约 1 天）：最小的一套可用操作** - 后台接口增加 `archive` / `restore` / `sensitive` 改标记（并入 `edit`，或单独做一个动作）；把 `forget` 的 hard（彻底删除）处理从 `lib/tools.js` 抽成一个公共函数，后台接口和工具都用它；详情页加"停用（或恢复）/ 彻底隐藏 / 标为敏感 / 标为不敏感"这几个按钮，再点一次确认只留给彻底隐藏。这一层沿用现有的 `store.memories.update` + `search.upsertMemory` + `audit.write`，不改存储格式。**顺带补上来源追溯**：`detail` 返回 `sessionId` / `sourceRange`；临时原文缓存的 `hb_…` 也支持只读详情；详情页给一个"展开来源轮次"的入口（沿用 `memory_recall` 的 `expandOriginal` 逻辑），否则 README 说的"带来源"在控制台里兑现不了。
2. **R1b（P1）：编辑** - `edit` 可以改 `content / entity / kind / temporal / importance / validUntil / todo`；会检查长度（如不超过 4000 字符）、重新算 `expiresAt`；正文一改就**清空 `chunks` / `embeddingModel`、清掉 `lastVerifiedAt`、保留 `sourceRange` 并标记为待重新核实**，再由后台重新生成语义检索数据；写操作记录 `memory-edited`（只记改了哪些内容项和 120 字摘要）。**不能只清语义检索数据**——否则代码类事实会继续显示"已核实"。**2026-11-08 定：编辑只算"订正"，不写证据、不加分**；要"印证（这条对）"走 R1c 的单独按钮，避免用户改个错别字就把证据分抬高。
3. **R1c（P1）：反馈** - 增加 `feedback`：`kind: reinforce | challenge`；写进 `evidence[]`，权重用 `evidenceWeights.user`（1.0）；用户点"这条对"（`reinforce`）时，`state` 这类记录会续期；写操作记录 `memory-feedback`；加每天 / 每条的数量上限和"撤销上一次反馈"，防止误点和刷分。**反馈前先过 `search.canAccess`**（不能给看不见的记忆写证据记录）。**2026-11-08 定：功能保留**（用得少也留，它是用户唯一能"教"记忆的通道）；做轻量版——详情页两个按钮 + 撤销 + 上限，不额外扩大投入，排在编辑之后。
4. **控制台**（`lib/client/browse-card.js` 详情页）：在"复制编号 / 正文"旁边加一组按钮；编辑用行内表单；操作完刷新详情和列表。
5. **一致性**：`search.upsertMemory`、`store.memories.update`、操作记录、`injectionLog` 都不受影响；不重启重新加载后数据还在。并发更新沿用现有的分类串行队列 + `update(fn)` 合并。
6. **测试**：后台接口这一层（R1a 停用 / 恢复 / 改标记、R1b 重新生成语义检索数据 + 来源位置失效、R1c 证据记录权重和数量上限）；页面这一层（按钮 / 表单 / 出错时的样子）；操作记录的检查。
7. **文档**：README 的"记忆管理"章节 + DESIGN §4.3 补上"用户也能操作"这条通道。

**收益**：把"按证据记录决定一条记忆的去留"从模型单向变成双向；用户第一次能"教"记忆系统，而不是只能删。**成本**：R1a 小、R1b/R1c 中。**风险**：编辑的含义要写清楚（编辑 = 修正，不等于印证；"这条对"走 R1c 单独的按钮）；重新生成语义检索数据要限速；反馈可能被误点，要能撤销。

**验收**：停用后能恢复；改了敏感标记后（要先打开 `sensitiveNoCross` 才生效——默认是关的），下一次自动带入按敏感 / 非敏感处理；编辑一条代码类事实后，旧的语义检索数据被清空、来源位置标记为待核实并重新生成；反馈后 `evidence` 多一条，且 `E` 的变化符合预期；彻底删除时的连带处理和工具那边一致；全量测试 0 失败。

#### R2a/R2b 导出与导入（先做导出，导入放后面）

**问题**：数据只存在本机 `~/.dsh/storages/memory`，是明文 JSON，没有校验，也没有版本号；换机器 / 重装 / 误删时，用户自己没有退路；要让用户信任长期记忆，代价很高。**注意**：今天手工拷贝目录也能做，所以这里缺的是"用起来顺手 + 能校验"，不是"数据完全带不走"。

**现状对照**：用户能用的导出 / 导入一个都没有；升级时的快速自检和构建产物属于工程资产。存储这一层不对外暴露目录路径（`lib/store.js`），所以导出应该走**把记录逐条转成文本**，而不是拷贝文件。

**方案**：

1. **R2a（P1，约 1 天）导出**：后台接口 `export` 返回 JSON（含 `formatVersion / exportedAt / pluginVersion / counts / memories / soul / profile / config 摘要`；**默认不含语义检索数据**，导入后按当前模型重新生成；临时原文缓存可选）；控制台"导出"按钮用浏览器直接下载；导出前提示"包含私密 / 敏感内容，只在本机使用"；写操作记录 `export`。
2. **R2b（P2，约 1–2 天）导入**：上传文件 → `importPreview`（条数、重复、冲突、敏感条数）→ `importCommit`。**导入是攻击入口，必须把现有的写入前检查重跑一遍**：`detectSecret`、`detectInjection`（敏感初筛默认关掉，只有用户自己打开敏感开关时才跑 `prescreenSensitive`）；`hidden` 记录默认不导入（这条规则要写明）；按编号 + 规范化后的内容合并重复；新编号存到磁盘；一次性提交（要么全成功，要么全不写）；限制文件大小（如 20MB）；写操作记录 `import`。
3. **备份**：文档里写清"先停掉 DSH，再复制 `~/.dsh/storages/memory/`"；要不要做一键"写一份备份副本"，取决于存储这一层是否对外暴露路径，第一版以导出下载为主。
4. **测试**：导出 → 清空 → 导入 → 查找结果一致；重复导入不会重复写入；损坏或恶意文件被拒，且不写脏数据；彻底隐藏的记录不会复活；敏感标记按当前设置决定（默认不标，用户打开开关才标）。

**收益**：数据能搬走、能备份，长期使用的心理门槛明显降低。**成本**：R2a 小、R2b 中。**风险**：导出文件里有隐私；导入可能夹带冒充指令的文字、密钥、敏感内容，或让彻底隐藏的记录复活，也可能写到一半失败，所以必须先试运行（dry-run）+ 过三道检查。

**验收**：导出的文件能被同一个版本导入，并且查找结果对得上；导入两次不产生重复；恶意文件被拒绝；彻底隐藏的记录没有被复活；导入失败不留脏数据。

#### R3 把使用情况存下来，看清它到底有没有用

**问题**：自动带入的日志只放在内存里，最多 60 条，**一重启或一改设置重新加载就清零**；没有 7 天的走势，没有成本，也没有反馈；用户没法回答"记忆到底有没有帮上忙"。

**现状对照**：`injectionLog`（`lib/injectionlog.js`）是有意不存到磁盘、不记正文和查询（隐私上是对的）；`audit` 里有管理动作，但不是每一轮的自动带入；总览页里"本次运行"只有自动带入 / 跳过的计数，记忆 / 临时原文缓存 / 待整理队列 / 语义检索覆盖率这些是存下来的数据（`lib/api.js:128-157,344-420`）。

**方案（最小可行）**：

1. **按天汇总表**（新的存储表，如 `metrics_daily`；按 DESIGN 的版本纪律，新增表不用升存储格式版本）：键是 `YYYY-MM-DD`，值是 `{ injections: {count, chars, records}, skips: {reason: count}, feedback: {reinforce, challenge}, extract: {done, failed, oversized, dead} }`。每轮自动带入或跳过时先在内存里累加，**每 30–60 秒或每 N 次写一次磁盘**，避免每轮都写；保留 90 天。
2. **后台接口**：`overview` 增加 `metrics: { days: [...7/30 天], totals }`；`injections` 这个动作保持不变（实时滚动记录），新增一个 `metrics` 动作。**注意**：按天汇总只能回答走势，回答不了"这次回答用了哪几条"；要回答后者，需要**另外按轮次保留最近 N 次自动带入的 `hitIds`（存在本地，只记编号 / 原因 / 字符数，保留 7 天，不记查询和正文）**——这是另一个存储决定，不能让按天汇总假装做到。
3. **控制台总览**：加"最近 7 天"卡片（自动带入次数 / 字符数、跳过的原因分布、反馈数、整理成功 / 失败 / 超大丢弃、模型用量（token）估算）和"最近 7 天自动带入走势"小图；`need attention`（需要留意）诊断卡接上超大丢弃 / 彻底失败的记录这些门槛值。
4. **把"为什么没自动带入"说细**：`no-hits` 分成 `empty` / `gate` / `budget` / `session-cap` / `already-injected` / `archived` 等子原因；试查页面带回 `gateDropped` 计数；`inject-error` 补上多语言文案；`health.warnings` 放到总览页；彻底失败的记录提示指向真正的查看入口（现在指向一个并不存在的"日志页"）。接上已经存在但没用起来的 `injections` 动作，给"查看全部自动带入"加筛选（按带入方式、原因、会话、工作区）和 `hitIds` 展示（点 `m_…` 用 `detail`；`hb_…` 需要补只读详情）。
5. **成本的说法**：自动带入的模型用量（token）≈ 字符数 / 4（中英混合可以配系数）；整理按"调用次数 × 平均输入字符数"估算，不承诺精确；面板上标注"估算"。
6. **操作记录查证**：操作记录页面从"只取 200 条"改成在服务端筛选 / 分页（存储上限 2000），并支持按类型（kind）和会话（session）筛选。
7. **测试**：用假时钟跨天、重启后数据还在、超过上限的清理、汇总算得对、`no-hits` 子原因的对应关系、`hitIds` 展示。

**收益**：从"此刻诊断"升级为"可回顾、可对比、可行动"；为后续调参提供真实数据。**成本**：中。**风险**：写磁盘的频率与隐私（只存汇总和编号，不存正文和查询）。**2026-11-08 定**：本机单人威胁模型，隐私不作为风险，规矩照旧（只存汇总和编号）；已按此收窄 §10 第 7 条。

**验收**：重启后最近 7 天的走势还在；自动带入一次后对应那天的计数 +1；超大丢弃 / 彻底失败的记录在总览页能看到。

#### R4 把"敏感自动标记"默认关掉（个人单人使用场景）

**问题**：`prescreenSensitive` 用的是 `lower.includes(keyword)`（`lib/text.js`），会对临时原文缓存的 `content + thinking` 做"包含这段字"的匹配。本机 5/5 条临时原文缓存都被误标成 `sensitive`，命中的几组词是：**emo 5/5**（都是 "memory" 里的一小段）、**NDA 4/5**（"standard / descendant" 这类英文词里的一小段）、**诊断 3/5**（"诊断卡 / 诊断工具"这类技术组合词）。而 `sensitiveNoCross` 默认开着，于是这些技术记忆失去跨工作区自动带入的资格。

**结论（2026-11-08 定）**：不做敏感自动标记，默认关掉。理由就是使用场景——本机单人使用、内容都是自己聊自己看，没有"别人看"的问题；敏感标记唯一的效果是"不跨工作区自动带入"，这条对个人使用没有价值，误伤却是实打实的。注意这和之前"修误报"是两种解法：修误报是把"包含就算"改成"更像才算"，但只要自动标记还在，就永远有误判；**默认关掉是直接消除这一类问题**。

**方案**：

1. **改默认值**：`sensitiveKeywords` 默认改成空（不再自动筛）；`sensitiveNoCross` 默认改成关。字段和设置项都保留，谁想用可以自己打开。
2. **整理提示词**：不再要求模型标 `sensitive`（字段保留兼容）；就算标了，默认配置下也不影响任何行为。
3. **手动标记保留**：并入 R1a，用户自己点"标为敏感 / 不敏感"，作为纯手动功能。
4. **文档**：DESIGN §2 那条"临时原文缓存写入磁盘时的那道最薄初筛防线"改成"可选的隐私隔离（默认关闭，个人使用不需要）"；README 同步。
5. **测试**：默认配置下，含 emo／NDA／诊断的技术文本不会被标敏感、不会被跨工作区拦截；打开开关并手动标记后，拦截仍然生效。
6. **如果以后要打开开关**，才回到"修误报"这条线：英文词加边界 + 中文多义词只提示 + 人工标注样本验收（见 §10 第 17 条）。现在不做。

**收益**：技术记忆的跨项目复用恢复；默认行为不再误伤。**成本**：小（约 0.3 人日：默认值 + 文档 + 测试）。**风险**：关掉之后没有自动隐私隔离——对单人本机使用没有实际影响；DESIGN 里"防线"的说法要同步改，免得文档和实现对不上。

**验收**：默认配置下，本机 5 条缓存不再因为是技术词被标敏感；跨工作区自动带入不再被敏感标记拦；手动标记 + 打开开关后拦截仍生效；README / DESIGN 措辞和默认值一致；全量测试 0 失败。

#### R13 工具行为的小修正（顺手就能做）

**问题**：四个工具整体上"能跑、安全、失败后知道下一步做什么"，但有几处实现漏了、有几处输出会失控。修起来很便宜，对信任和上下文额度却很有价值（这些证据都来自一次专门针对工具使用情况的检查）。

**方案（不改存储格式版本；只加一个可选字段 `confirmedByUser`）**：

1. **修 `source` 标错来源（最优先）**：`memory_remember` 目前一律写成 `source:'user'`（`lib/tools.js:351`）；但**不能简单改成 `confirm ? 'user' : 'assistant'`**——`confirm` 是模型可以自己填的参数，模型完全可以自己传 `confirm=true` 来"证明"用户说过，`stagedBy` 同样是模型自己报的。**2026-11-08 定：来源按下面的顺序判定，全部不依赖模型自报。** ① **整理出来的记忆（占大头）**：整理流程写进来的每条都带来源区间（`sourceRange`），回到该会话的事件流看这段原文是谁说的——全是用户回合 → `source:'user'`；全是助手/工具回合 → `source:'assistant'`；混合的保守记 `'assistant'`（宁可低估，不误标用户）。角色是 DSH 本体给的，模型改不了。② **模型主动记（`memory_remember`）**：新增可选参数"用户原话引用"（`userQuote`，**不要叫 `quote`**，`source` 枚举里已经有一个 `'quote'` 表示"用户转贴的外部资料"），工具做规范化后校验它确实出现在本会话的用户消息里——校验通过才记 `'user'`，否则记 `'assistant'`；模型可以挑一句真实原话，但造不出来。③ **用户界面确认**：用户在控制台点确认，是工具之外的可信信号，记 `confirmedByUser`（措辞"你确认过"），走 `/memory/api` 的确认通道，不经模型。④ 自动带入 / 工具回显的措辞分三档："你之前说过"（user）/ "助手之前记下的"（assistant）/ "你确认过"（confirmed）。⑤ 旧记录：有 `sessionId + sourceRange` 的按 ① 重算一遍；没有的标"来源查不清"，不猜。同步改 DESIGN §4.2 的措辞约定，并把"原文角色"这个依赖纳入 R25 的兼容测试。
2. **`memory_recall` 结果截断要标注 + 加 `limit`**：多取 1 条，用来判断后面还有没有；结果末尾加一句"共显示前 N 条（还有更多，用 time 或更具体的查询收窄）"；新增 `limit`（1–20，默认 10）。成本约 15 行 + 2 个测试。
3. **`memory_forget` 的"同一对象的相关记忆"加上限**（如 10 条）+ 总数；否则记忆库越大，一次 `memory_forget` 回显的内容越大。
4. **不再做自动敏感初筛**：默认配置下 `sensitiveKeywords` 为空、`memory_remember` 也不做敏感内容初筛（见 R4 / §10 第 3 条），避免把技术文本误标；如果用户以后自己打开敏感标记，这里再沿用 `prescreenSensitive`（`lib/text.js`）补标记。
5. **`memory_remember` 的 `kind` 去掉 `episode`**：`kind` 和 `temporal` 是两个维度，`kind='episode'` 会被渲染成"当时聊过"（`lib/inject.js:138-139`），和用户的本意冲突；明确让用户记的只保留 `fact` / `lesson`（话题摘要由后台整理那一侧生成 `episode`）。
6. **自动带入的行里带上记忆编号（可配置 / 在额度内）**：`mem` 行前面加 `[m_…]`，让模型能对"刚看到的事实"直接调 `memory_forget({id})` 或者纠正；编号约 40 字符 × ≤5 条，计入现有 1500 字符额度，得先跑一轮自动带入额度的测试。
7. **工具描述瘦身**：四个工具的定义实测 1,992 字符（查找 604 / 写入 612 / 删除 338 / 人格设定 438），大约 1/3 是"把参数规则写在描述里 + 和参数说明重复"；按 DSH 的"智能体使用体验"规范把规则搬回参数，预计省 ~300 字符，规则也更容易被模型抓住。
8. **补一句边界**：`soul_update` 的描述加上"偏好和事实写进记忆，性格和口吻写进人格设定"；`memory_recall` 的描述补上三类真实触发（用户提到过去的决定、接着上次的任务做、要求引用原话或资料）和一条"上下文已经够了就不要调用"。
9. **用户画像截断保护（P0 小修）**：外部画像文件超过 20,000 字符时，`profileSnapshot` 只返回前 20,000 字符并标 `truncated`；用户编辑后一保存，就会**把截断后的版本写回去，尾部内容永久丢失**。修法：`truncated=true` 时禁止保存（或先写一份 `.bak` 备份，并在页面上明确提示），`profileSave` 增加"源文件超长"就拒绝；这是真正的数据丢失，不是体验问题。

**收益**：把来源标错的问题消掉（信任）、把悄悄截断的问题消掉（额度）、去掉自动敏感标记的误伤（默认关闭）、让模型能对自动带入的记忆做处理。**成本**：小。**风险**：行里带编号会占额度；建议先只给长期记忆那几行加，跑过自动带入额度测试再全面铺开。

**验收**：来源判定三档各有测试（用户回合 → user、助手/工具回合 → assistant、模型主动记但没引用用户原话 → assistant、界面确认 → confirmed，旧记录按来源区间重算或标"查不清"）；`memory_recall` 的截断有标注且 `limit` 生效；`forget` 回显有条数上限；默认配置下技术文本不被标敏感（打开开关后手动标记仍生效）；自动带入的额度测试不超过 `injectMaxChars`；超长画像禁止保存 / 有备份；全量测试 0 失败。

#### R18 只用关键词匹配时的默认门槛校准（改一行默认值）

**问题**：绝大多数用户不会配语义检索，实际用的是纯关键词匹配这种模式；而这一模式的相关性门槛默认 `bm25OnlyMin=2`，偏松。在固定评估集 `frozen-v2` 上重算：混合模式里不该命中的查询 2/13、平均 0.77 条；**纯关键词匹配模式里不该命中的查询 6/13、平均 2.15 条**（连"天气 / 股市"这种闲聊也各带入了 4 条）。把 `bm25OnlyMin` 提到 10，不该命中的查询回到 2/13，前 1 条命中率 0.973→1.000，前 5 条命中率不变。

2. **两条评估路径分别算**：`tools/eval-frozen.mjs` 增加 `--lane bm25|hybrid|both`，`bench-results/frozen-v2.json` 同时存两组指标；README / VERIFICATION 的指标表按评估路径分行，避免再出现"前 1 条命中率 1.0 只对配了语义检索的用户成立"这种误读。
3. 小记忆库的保护措施保留（`bm25OnlyMinPoolSize=30`），免得新用户头几十条被错误拦掉。
4. 文档：把"默认质量"和"混合质量"分开写；评估验收从"不该命中的查询 ≤1"改成同时约束纯关键词匹配这条路径。

**验收**：`frozen-v2` 的纯关键词匹配路径上，不该命中的查询 ≤2/13；前 1 条命中率不下降；`check:ledger` / `check:conform` 通过。

#### R6 用户画像晋升

**问题**：用户画像是每轮都会自动带进对话的一层，对缓存友好，价值也最高；但唯一的入口是手工编辑 md 文件。绝大多数用户不会去写，这一层等于被放弃了。

**方案（两条路，先做便宜的那条）**：

- **最小版本（推荐先做）**：在控制台的画像页加一个按钮"从记忆生成画像候选"：在 DSH 本体一侧先筛（`temporal=pattern`、证据充分、**只取 `entity=user`** 或本工作区里出现最多的对象），生成 5–10 行候选文字 → 用户在文本框里删改 → 保存写入 `profileFile`（沿用现有的 `profileSave`，整份一次写入，并记操作记录）。**绝不自动写**。候选由**固定模板**生成（不调用大模型），零调用成本；如果要用大模型，必须单独立项。**2026-11-08 定：候选必须附带相关证据**——每条候选要能点开看到它来自哪几条记忆（编号可点开）、证据有几条、最近一次被印证是什么时候；没有证据的候选不进列表。
- **完整版（DESIGN V2 里已经规划）**：在后台整理用的提示词里加上 `profileCandidates`，以 `entity='profile'` 放进待确认区；画像页显示"待采纳候选"，用户改完再采纳 → 追加到文件，同时把候选停用（和人格设定的提议通道是同一套做法：`entity='soul'` + `soulAdoptProposal`，`lib/api.js:660-681`）。
- **边界**：保存前查一下候选和 `AGENTS.md` / 人格设定有没有重复（只提示，不自动改）；`profileFile` 为空时先引导用户设置文件路径。

**收益**：让每轮都带进对话的那一段真正有个性化的内容；把 V2 的规划提前做掉一部分。**成本**：中。**风险**：候选可能片面或者泛泛而谈；坚持"用户改过之后才写"，不做自动晋升；项目层面的事实不要写进用户画像。

**验收**：生成候选不写磁盘；采纳后下一轮的画像段落就生效；操作记录里查得到；上限 20k 字符。

#### R8a/R8b 超长回合不再悄悄丢掉

**问题**：把单个回合还原成原文时（`renderOriginal` 会把工具输出全文拼进去，`lib/hotbuffer.js:31-43` 没有任何截断），只要超过 `extractMaxInputChars=65536` **个字符**，这个回合就会被整条跳过、标成等待删除，48 小时后真正删除（`lib/extract.js:572-591`）。本机 3/5 条临时原文缓存因此消失。而写代码这类场景最值钱的恰恰是长会话；这个上限又不在记忆页上能改的地方。

**关键约束**：`renderOriginal` 同时被后台整理、`memory_recall` 整条展开和复盘使用（`lib/extract.js:115,122`、`lib/tools.js:100`）——**不能全局截断**，否则"`memory_recall` 展开原文"就被破坏了。截断只能作用在整理这一条路径上。

**方案**：

1. **R8a（P0，约 0.5–1 天）：只截整理时的工具输出** —— 新增 `extractToolOutputMaxChars`（默认 8000），在 `turnText()` 渲染之后、放进这一批之前，把工具输出那一段截短；用户和助手的正文、以及报错特征都保留。单回合上限直接用现成的 `hotBufferTurnMaxChars=32768`，**不再新增一个数值相同的第二个旋钮**。
2. **R8b（P1，约 1–2 天）：回合内留头留尾并做标记** —— 如果整轮还是超限，就用 `makeExcerpt`（留头 60%、留尾 40%，`lib/text.js`）截到上限再放进这一批；提示词顶部加一句"〔本回合已截断〕"；操作记录里写 `extract-truncated-turn`（记录原长和截后长度），不再标成等待删除。仍然坚持"不跨回合拼接、不跨回合截断"——这和 DESIGN 现在写的"整条舍弃"正好相反，需要记一次 DESIGN 版本升级。
3. **让用户看得见**：总览页的"需要关注"里显示最近被截断、被丢弃的条数；设置页说明 `extractMaxInputChars` 这个取舍。
4. **测试**：造一个超过上限的单回合，断言"至少一条记忆真的存到磁盘"和"有截断记录"同时成立（不能二选一就算过）；不新增等待删除的记录；`memory_recall` 展开原文的长度不受影响；调用大模型的次数有上限。

**收益**：长任务和团队会话不再"白聊"；彻底失败的记录比例明显下降。**成本**：R8a 小，R8b 中。**风险**：关键结论可能正落在被截掉的中间段——用"留尾 + 截断标记 + 整理提示词里说明"来缓解；默认上限仍然是 65,536 个字符，不往上提，免得单次模型调用成本爆掉。

**验收**：R8a 之后，本机超过 65,536 个字符的回合能被整理（不再整条跳过）；R8b 之后，超长回合会留下"截断记录 + 至少一条记忆"；`memory_recall` 和复盘拿到的原文长度不变。

#### R9 记忆的清理与容量

**问题**：现在只增不减：没有容量、重复、过期的日常检查；待整理队列里状态为跳过或彻底失败的记录永远不清；等待删除的记录没法重放；用得久了，用户也不知道这一池子记忆到底健不健康。

**方案（先只读，后操作）**：

1. **记忆健康检查（只读）**：给出条数和占空间的估算（把每条记录的 JSON 长度加起来）、按状态/类型/工作区/存了多久的分布、重复候选（内容规范化后相同，并且是说的同一个对象、字面高度相似；不自动合并）、很久没被验证过的代码位置引用、已经过期的 state、证据不足的条目、被反复查找到续了有效期却从没被印证过的条目（见 §10 第 15 条）、等待删除的记录清单、临时原文缓存里还没整理的条数、待整理队列里的垃圾行数。**性能上要注意**：找重复候选别拿全池两两对比（数量一多，计算量就爆炸），先按说的对象（项目/人/模块）分桶，再用快速相似度估算（MinHash）或者按前缀过滤；20k 条规模的页面和巡检要有 95% 的情况下的上限目标（比如 ≤500ms）。
2. **总览页加一张"记忆卫生"卡**：显示 3–5 个关键指标和"查看"入口；不制造焦虑，只在超过门槛值时提示。
3. **可做的操作（可选，都要用户确认）**：一次停用一批已过期或证据不足的、停用重复条目里较旧的那条、清理待整理队列里超期的跳过行和彻底失败行（**清理前先把摘要写进操作记录**，否则"为什么没记住"这条唯一线索就没了）、重放等待删除的记录（前提是它的临时原文缓存还在）、清理已经整理过的临时原文缓存；**不做自动删除**（DESIGN §9）。
4. **测试**：门槛值是确定的；分页；空池和大池都要覆盖；重放失败要能说清原因。

**收益**：用得久也撑得住；把 DESIGN 里已经承诺、但 ROADMAP 上一直缺的"重放等待删除的记录"补上。**成本**：中。**风险**：先只做只读，避免误删；**性能边界**：`list` 会把全部记录遍历一遍并返回完整正文，20k 条的池子必须分页、只取部分内容，检查时按说的对象分桶，否则页面会卡。**2026-11-08 定**：2 万条时列表第一页 ≤500ms、总览 ≤300ms、导出边读边下不卡；先定目标，有真实数据再实测校准（见 §10 第 22 条）。

**验收**：池子里 0 条、3 条、几千条时都能正常打开；重复候选由人自己确认；任何操作都能在操作记录里查到。

#### R14 去重本身就是一次印证

**问题**：去重命中的时候只记一条操作记录，不记证据（`lib/extract.js:736-744`；`lib/tools.js:344`）——用户反复确认、或者反复出现的事实，证据得分仍然可能是 0，照样会随时间慢慢降权，最后退出候选或被停用。

**方案**：去重命中、并且原来那条是 `status==='active'` 时，补写一条 `kind:'reinforce', weight: evidenceWeights.system`（0.5）的证据；同一批里同样的内容只记一次（用 batchKey 或内容键去重）；顺便给进行中的事项续期。**`negativeSince` 只有在这条没有用户"质疑"过的时候才清**——用户点过"质疑"的条目，系统重复再多也不能替用户翻案，必须用户明确确认才能清。`memory_remember` 命中已经生效的条目时同样补一条，返回文字改成"已印证（第 N 次）"。落点：`lib/extract.js` 的去重分支复用已有的 `pushEvidence`/`reconcileArchiveState`；`lib/tools.js:344`。

**收益**：反复出现的事实不会再被降权吃掉；"记过"和"经常记"从此能区分开。**成本**：小。**风险**：有人会刷分——用系统权重、同一批只记一次、不改动它的时间类型来限制；**清 `negativeSince` 可能盖掉用户的质疑**，必须加一道"用户质疑过就不清"的保护；建议先把固定评估集里的用例扩一扩，确认排序没变。

**验收**：同一内容连续出现 3 次后，系统给的证据会增加；没有用户质疑时 `negativeSince` 清零；有用户质疑时 `negativeSince` 保留；去重不产生新记录；全部测试通过。

#### R15a/R15b 整理过程要看得见，收尾要及时

**问题**：整理失败、找不到该走哪条路、失败后正在等下一次，这些情况全都只写进 `logger.info`；用户看不到"上次整理是什么时候、为什么失败"；也没有手动触发的入口；会话结束时不会立刻整理一次（要等 5 分钟，或者等下次启动）。

**方案**：

1. **R15a（P0，约 0.5–1 天）：状态和操作记录** —— `stats()` 里增加 `lastExtract:{at, ok, reason, batchTurns, chars}` 和 `drops:{lowConfidence, injection, secret, oversized}`；失败时，在第一次失败和最终彻底失败各写一条 `extract-failed` 记录（按 batchKey 限制频率，不要刷屏）；总览页的健康检查里也报"上次整理失败"。
2. **R15b（P1，约 0.5 天）：手动触发 + 收尾** —— `/memory/api` 增加 `flushNow`（可以带 sessionId，60 秒内只允许一次），总览页给一个"立即整理"按钮（点之前要二次确认，并提示这会消耗一次模型调用）；整理这一侧订阅 `agent/disposed` 事件（事件早就有了，`inject` 那边已经在用；注意清理的先后顺序），一收到就对那个会话执行 `scheduleFlush`；第一轮可以用更短的 `extractFirstTurnIdleMinutes`（默认 1）——没有界面、跑在后台的场景仍然没法保证退出前整理完，但"关窗口、切会话"这类高频情况当天就能看到长期记忆。
3. **测试**：用假模型制造失败 → `lastExtract.ok=false`，并且操作记录里看得到；`flushNow` 能触发并真的存到磁盘；会话销毁后会自动整理；频率限制生效。另外补"空闲触发"这条路径的测试（现在所有测试都用 `extractBatchTurns:1` 绕过去了，见 §10 第 13 条）：造一个攒不到 6 轮的会话，等空闲时间到，能真的整理出记忆。

**收益**："记不住"不再是玄学，而是一个能解释的状态，用户能自己救。**成本**：小到中。**风险**：`flushNow` 被滥用 → 加频率限制和二次确认。

**验收**：失败看得见、能再试一次、手动触发有限流；会话一结束就立刻进整理队列。

#### R16 关掉整理时，给临时原文缓存一个真实的上限

**问题**：`extractEnabled=false` 时，系统只往临时原文缓存里写，不登记待整理队列；而"还没整理、又不是等待删除"的临时原文缓存永远不会过期（`lib/hotbuffer.js:118-133`）。用户以为自己只是省了模型调用，实际上历史原文会一直参与查找和自动带入，而设的那道兜底限制在这个状态下等于没起作用。

**方案**：新增 `hotBufferUndigestedTtlHours`（默认 168 小时，可以配成 0 表示关掉）；`sweep` 对两类临时原文缓存做处理并写下 `hot-dropped-undigested` 记录（写明原因）：一是用户主动关掉了整理，二是还没整理、且已超过有效期。**要把两种情况区分开**：模型服务临时不可用（退到备用方案）时继续"不过期"；只有用户主动关掉（改设置）才启用这个上限。**删除之前必须确认原文还能从会话日志里取回来**（`sessionQuery` 读得到，而且没过期）；读不到就**保留并告警**，不能默认真正删除——还没整理的临时原文缓存可能是唯一一份，而 DESIGN §9.9 只允许删"已经整理过的临时原文缓存的副本"，所以这条也要记一次 DESIGN 版本升级。

**收益**：磁盘占用和自动带入里的噪声都有边界；设置项的语义也更诚实。**成本**：小。**风险**：关掉整理之后又想找回原文 → 靠文档说明和操作记录；**误删唯一一份**是主要风险，用"先检查读得回来 + 读不到就保留并告警"兜底；不建议默认设成 0。

**2026-11-08 定：同意按上面的做法拆开两种情况**；删之前先确认原文能从会话日志读回来，读不到就保留并告警（见 §10 第 12、18 条）。

**验收**：关掉整理 7 天后，临时原文缓存不再无限增长；操作记录里写明每条是"丢弃"还是"保留"及原因；会话日志读不出来时，缓存被保留并告警；模型退到备用方案期间，缓存仍然不过期。

#### R19 说的对象覆盖门槛（实验）

**问题**：查询里点名的对象（比如 omega 或某个私有项目）根本不在池子里时，按字面相似度做的匹配会把别的对象的记忆塞满 5 条；现有的相关性门槛只看匹配得多强，不看"说的是不是同一个东西"。

**方案**：在自动带入的相关性门槛之后再补一道**对象覆盖检查**：从查询里取前 1–2 个高 IDF 词（越少见的词权重越高；拉丁字母或标识符优先，长度 ≥3；中日韩文字用 3-gram 加上这个权重来排），要求候选的 `content` 或 `entity` 至少覆盖其中一个，否则丢掉。只对 `purpose==='inject'` 生效；跨语言的查询不启用（或者按"查询和记录是同一种语言"来判断）。落点：`lib/search.js` 的相关性门槛那一段（294-309 之后）。**更省事的变体**：把现有的 `entity` 从"加 ×1.1 分"改成"已知对象必须匹配"的准入条件——**后置过滤近似重算** frozen-v2 的结果：前 1 条命中率、前 5 条命中率不变；每个该命中的查询平均拿到的条数 5.00→1.35；前 5 条里相关条目的比例 0.22→0.80；再加一条"不认识的对象，查询必须覆盖关键词" → 不该命中的查询 0/13（前 1 条命中率 1.0→0.95）。这两个数字必须在真实的自动带入路径上再验一遍，不能直接当成收益承诺。

**收益（按 frozen-v2 重算）**：不该命中的查询从 2/13 降到 **0/13**；前 5 条里相关条目的比例从 0.22 升到 0.80；代价是每个该命中的查询平均拿到的条数从 5.0 降到 1.0–1.35（丢掉的正是"别的对象的同模板噪声"）。**成本**：中。**风险**：真实池子里，同一个项目的条目未必都重复项目名（比如"这个项目的端口是…"），会被误杀；**必须先跑 `inject-eval`（450–600 条的池子）再定门槛值**，并且做成可以关掉的设置；跨语言的查询会被误杀，得按语言分别启用。

**验收**：在真实池子上，不该命中的查询不增加，该命中的查询前 5 条命中率不下降；有开关能关掉；能给出逐条查询的对比差异。

#### R20 自动带入的额度联动

**问题**：默认是 5 条 × 300 字符，可总额度只有 1500 字符，根本装不下（要放 5 条，平均每条得 ≤271 字符）。片段写到最满的时候，实际只带进了 4 条；一超限就"整条丢掉"，结果一条长的会把后面短的挤掉。

**方案**：① `excerptChars` 改成按还能用多少额度动态取值（`perItem = floor((injectMaxChars - header) / min(injectMaxItems, 候选数)) - prefix`，下限 120）；② 超限时**只截断最后一条**（末尾留"…"），而不是整条丢掉；③ 把"因为额度不够、超过会话上限、重复、已停用而被丢"的情况写进自动带入日志的计数里（`dropped:{budget,session,dedup,...}`）。落点：`lib/inject.js:576-592`、`lib/search.js` 的 `excerptFor` 增加一个 `maxChars` 参数、`injectionlog` 这一项。**顺带修一下试验台（控制台里用来试查的页面）的统计标准**（现在预览默认给 8 条，比 `injectMaxItems=5` 还多，而且不按这个数截断；"不指定（全部）"在没有本地工作区时其实会触发刚开始用时的收紧和隐私过滤）：预览按 `cfg.injectMaxItems` 截断、默认值从 overview budgets 取、返回 `gateDropped`、文案改成"本地没有工作区时按这个来"。

**收益**：默认配置下有效条数从 4 条变成 5 条；长条目不再"一口把额度吃光"；"为什么只看到 4 条"能解释清楚；试验台调参时不再用错统计标准。**成本**：小。**风险**：截断会丢掉尾部信息（有 `…`，而且用 `recall` 还能展开全文）；`excerptChars` 的含义变了，要在 DESIGN §4.2 里写明。

**验收**：默认参数下自动带入 5 条、总字符 ≤1500；被丢掉的原因能在自动带入日志里看到。

#### R21 D3 跨层去重换一个判断依据

**问题**：D3 这条要求"同一个 session 里，长期记忆的原文必须是临时原文缓存的逐字子串"；只有 1–2 条人工构造的单元测试，在 frozen-v2 上一对都没命中，线上到底能不能命中也不好说——等于只是名义上交付了。其实长期记忆自己的 `sourceRange` 明明就能用来判断是否重叠。

**方案**：把判断依据改成"**长期记忆的 `sourceRange` 和临时原文缓存的 `[startSeq,endSeq]` 有重叠（同一个 session）**→ 就折叠临时原文缓存（保留长期记忆）"；有争议、被取代、还在待确认区这几类排除条件照旧保留；被折叠的临时原文缓存仍然能被 `memory_recall` 查到。落点：`lib/inject.js:98-121`（可以照抄 `hotIsShadowed` 读取范围的办法）。再补一条固定评估集和整个流程上的测试。

**收益**：D3 从"名义上有"变成真的会触发；少一处重复展示。**成本**：小。**风险**：一批长期记忆覆盖好几轮时，可能把"用户原话"一起藏起来——这需要产品上做判断；保守的做法是只在"这一轮的临时原文缓存被本批长期记忆完全覆盖"时才折叠。

**验收**：新增的测试能在同一个 session 下触发折叠；有争议、被取代、在待确认区的不折叠；CHANGELOG/STATUS 里对 D3 的说法和代码实现一致（或者标注"部分交付"）。

#### R22 把查询补全一点

**问题**：查询只有当轮用户说的话，所以"继续""那个呢""上周说的端口"这类问法一条也命中不了；`turns.recentTexts` 已经缓存了最近几轮的文字，却只拿去判断对象。

**方案**：查找用的查询 = 当轮用户说的话 + 最近 1 轮用户说的话（截到 200 字符），而且只在查询短于 12 个字符、或者含有指代词（这个/那个/继续/然后/改成/它）时才拼上去；拼出来的东西只用来查找，不用来写入。时间上的指代（昨天/上周）解析成 `timeWindow`，取"时间窗内"和"相关性前 N 名"两拨的并集（`search.list` 已经支持 timeWindow）。落点：`lib/inject.js:435-445` 加上 `turns.recentTexts`。

**收益**：专治"继续""那个呢"这类最常见的真实失败，对话的连贯感能恢复。**成本**：小到中。**风险**：上一轮的噪声被带进查询 → 所以只对短查询启用，而且拼上去的部分权重减半；会话刚开始（进程刚起）时 recentTexts 是空的，第一轮没效果。

**验收**：固定评估集里增加"追问"这一类查询；短查询的命中从 0 开始往上走；长查询和正常查询的前 5 条命中率不下降。

#### R23 关系候选加一条"同一对象"通道（D2b 的前提）

**问题**：现在的关系候选，是拿整批原文当查询、按相似度取前 8 名，再在本地过滤一遍；结果"争议"的那一端（`m_alpha_db_alt`）遇到事实类查询时，用关键词匹配排到 42/204，永远进不了候选；"更新"的那一端则被 `supersededFactor=0.3` 挤了出去。门槛值怎么调都治不了病根：字面看着相似，说的并不是同一个对象。

**方案**：`purpose='relation'` 多加一条**同一对象通道**：`entity` 相等且不为空，或者同一个 workspace、同一个 kind 的候选，先占掉名额（比如前 8 名里保底 4 席），剩下的再按相似度排；关系评估改成用"整理那一刻之前的状态"来跑（先把 `_old`/`_alt` 上的 `supersededBy`/challenge 去掉再跑），否则 0.375 里混着事后才知道的信息和真正的失败，没法拿来指导调参。落点：`lib/search.js` 的名额分配 + `tools/eval-frozen.mjs`。

**收益**："冲突"的那一端能被找回来，"更新"的那一端不再被降权挤出去——直接服务 0.7.0 的 D2b。**成本**：中。**风险**：候选变多会稀释按相似度排出的前几名，需要逐条查询看差异；合错的风险由 D2a 的保护措施兜着。

**验收**：关系候选能找回来的更多，同时关键的"不该命中"零违规；试运行的对比差异可复现；固定评估集里的关系类用例扩到 ≥20 条。

**2026-11-08 定（方向 B）**：跨时间类型的取代，按"同一个对象 + 新记录更晚 + 内容里有明确改口表述（现在改成 / 不再 / 已经换成）"来设计样例和跑新旧对比；对比结果不满足"漏盖明显下降 + 误盖不上升 + 自动带入里的矛盾不减少"就不改默认，只留开关（见 §10 第 11 条）。

### 5.3 P2：查找与协作增强（建议 0.8+）

- **R10 按会话暂停**：新增工具 `memory_pause({ minutes? })`（用户说"这段别记"时调用），或者在控制台给一个会话开关；暂停状态按会话记，并且会自动到期；暂停期间不写临时原文缓存、不进待整理队列，也不自动带入；操作记录里写 `session-paused`。**边界要写清楚**：当前回合的临时原文缓存在回合结束时已经写下去了，如果"这段别记"只对下一轮生效，这一轮还是记进去了——所以需要定义"当前轮怎么撤回或删掉"（至少把本会话当前轮里还在排队、尚未处理的记录标成跳过或彻底隐藏）；**防止滥用**：模型可能被外部内容诱导去调 pause，建议要求用户确认，或者只保留控制台开关；它和工作区停用的区别要写进 README。可选的扩展：**软静音**（"别再提"）——不删除也不隐藏，只是在自动带入时压住，`recall` 里仍然查得到并标上"已静音"；这需要新设置项（`mutedUntil`）和一次存储格式版本升级，放在 P2。
- **R11 工具功能增强**：`memory_update`（按编号纠正或补充一条，沿用 `supersededBy` 和关系那一套保护措施；这是"模型发现代码或偏好变了"时唯一不会把证据链弄断的通道）；`memory_confirm/id`（由模型一侧确认或拒绝待确认区的条目，P2）；自动带入时给出条目编号、以及 `memory_recall` 的过滤，已经并入 R13。要注意：**`memory_status` 是假需求**（模型不需要知道这些管理状态；"为什么没想起来"对用户和调参的人才有意义），不要做成工具，只在 `memory_recall` 结果为空时加一句提示，区分"确实没记过"和"可能被相关性门槛拦下了"。可选：`recall asOf`（顺着取代链查"某个时间点当时相信的是什么"），需要 `supersededAt` 这个设置项和一次存储格式版本升级，P2 实验。
- **R12 协作与人格**：子代理怎么处理——写入这一侧现在完全不看 `session.header.origin`（读取那一侧却会跳过），子代理的工具循环照样会写进库里。建议先做"标记来源 + 记忆页能筛选 + 操作记录"，**默认值不要拍脑袋决定**：当前本机 3/3 条长期记忆、4/5 条临时原文缓存都来自子代理，直接默认成"不记"可能让池子空掉；用真实使用数据来决定（可选设置 `recordSubagents`，打开时打上 `origin='subagent'`，排序时降权）。要把团队记忆、任务记忆的边界定清楚（和 DSH 任务板分工）；人格设定自己改过之后，在总览页显示"最近变更"；本地运行的小模型（ONNX）提供的语义检索按 V2 的规划推进。**2026-11-08 定：默认值不拍脑袋**——先做来源标记 + 开关 + 按来源筛，默认值等你本机真实使用测试之后再定（见 §10 第 8 条）。
- **R17 轻量的"同对象一起出现"索引**：启动时或增量地在内存里建一张相邻关系表（`entity -> memoryIds`、`entity -> coEntities`；来源是：同一条记录、同一次会话、同一批 filePaths），查询时把命中的对象向外扩一跳，给候选加权，关系候选集也用它补齐前 K 名；不存到磁盘，也不引入图数据库。目标：改善"问某个人或某个项目时，能把散落在各条记忆里的事实一起找出来"。风险：名字相同但不是同一个、跨工作区的隐私、启动耗时跟条目数成正比；必须能关掉，并且在固定评估集上验证。
- **R25 与 DSH 本体兼容的防回退包**：把"本体升级以后，自动带入不能整轮失败"做成自动检查：扩展 `check:host`/`check:shapes`，覆盖新用到的 DSH 本体接口；给自动带入的消息加一层兜底——"形状不合法时退成普通文本或者跳过，而不是直接报错"；新加的表和新加的 `global` 设置项（R3/R5 会用到）补上数据迁移测试；在 CI 里跑"上一版 session 格式 + 当前版本"的兼容矩阵。**接口安全这一块按 2026-11-08 的结论收窄**（这属于 DSH 本体的安全问题，插件不做自己的登录 / 鉴权）：插件侧只做两件事——README 写清"同源不等于鉴权，威胁假设是本机单人使用"；部署模式判断跟随 DSH 本体提供的信号（本体以后有登录或回环判断就直接用），并补上 Origin 不匹配、GET、非 JSON、请求体过大这几类测试。风险：功能越多维护面越大，这正是 DESIGN §12 已经承认的长期风险。
- **R24 按剩余时间决定怎么查**：给 `search.search` 传剩下还有多少额度、或者一个 `deadlineMs`；语义检索这一路在"剩余额度 < `semanticSearch.timeoutMs`"时直接不参与（等于退成只用关键词匹配），而不是等到超时以后再把整轮丢掉。落点：`lib/search.js:244-248`、`lib/inject.js:527-530`。收益：端点慢的时候，从"这一轮干脆不带任何内容"变成"用关键词匹配带进去"；README 里建议的 `timeoutMs=600` 也就不再和 300ms 打架。风险：`inline-timeout` 的含义变了，需要跑防回退测试。

### 5.4 不建议做（守住边界）

| 想法 | 为什么不做 |
|---|---|
| 让模型给结果重排（rerank） | 违背"不打扰聊天"和 300ms 的时间额度；DESIGN §9 已经明确不做；现有的相关性门槛已经挡掉大部分噪声 |
| 引入专门的语义检索数据库或图数据库 | 单机几万条以内，用 JSON 加内存就够了；多出来的重依赖和部署成本不成比例 |
| 自动合并、自动删除记忆 | 删错的代价很高；符合"宁可重复，不可误删"的原则；只给建议，由用户确认 |
| 自动把画像、人格写进用户画像和人格设定 | 会让用户失去解释权；现有的人格设定提议通道已经证明"人工确认"是对的 |
| 云端同步、多端共用 | 隐私上的前提是"本机单人"，上云就改变了威胁假设，那是另一个产品 |
| 用记忆插件做提醒、闹钟 | DSH 本身就有 `schedule_*`；插件只记待办和截止时间，不抢别的职责 |
| 用记忆插件替代 AGENTS.md | 规矩必须确定，记忆只是概率性的数据；两边分开是对的 |

## 7. 和 DSH 自带的能力比一比（避免重复造）

| 查原文 | `sessionQuery` + 会话搜索工具（是否启用看当前配置档案） | `memory_recall` 查整理后的记忆；原文可以再展开（从会话日志里读当时的对话） | 两个入口：先查记忆里的事实，细节再回会话里找 |
| 对话压缩 | `dsh-compaction` + `tokenMeter`；大约到 80% 就触发 | 监听 `compaction/*`，压缩后按字符把记忆补回来，并解除"本会话已经带过就不再带"的限制 | 不抢压缩的活；重点看“压缩后有没有重复带入” |
| 上下文压力的估算 | `tokenMeter`：按 4 个字符算 1 个模型用量来估，中文这类字符（CJK）会被低估 | 读 `contextPressure`，超过 0.85 就跳过这一轮的自动带入 | 这个数字不是用来计费的；中文下实际更保守 |
| 工作区身份 | `workspaceRegistry`、DSH 本体给的 `workspaceId` | 所属工作区 = git 根目录 + 子路径；v1.16 的选择器把三个来源合并了 | 两边编号的算法不同，长期建议把 DSH 本体的编号也记下来 |
| 多个 agent 协作与任务板 | agent teams：成员名册、任务用版本号做并发占位、共享当前工作目录、不跨进程 | 全局的记忆池；子代理默认不自动带入、但会写进来 | 团队里的临时状态归任务板，长期事实归记忆；现在缺“这条归谁”的说明 |
| 操作步骤类知识 | skills／文件系统里的技能 | `lesson` 存的是陈述性的经验，不是一步步的做法 | 不存具体工具的打法；“怎么做”归技能或 `AGENTS.md` |
| 提醒与定时 | `dsh-goal`、`dsh-schedule` | 没有闹钟；只在对话开场带一次 | 不自己做调度器；到期的待办只在开场时“冒一下” |
| 安全边界 | `sandbox`、`approval`、`credentials`、`storageDomain` | 隐私处理只管自动带入和跨工作区，不是安全边界 | 不要把 `privateWorkspaces` 说成“能防越权” |
| 界面与设置 | 侧栏插槽、`configForms`、保存后立刻生效的设置不用重启就能更新 | 7 个页签的控制台、28 个可写设置项 | 控制台继续补“能动手操作”的功能，不要只加只读卡片 |

**容易冲突的 6 个地方（判断）**：

1. **行为规矩 vs 用户画像／人格设定**：这三处都可能写“用户喜欢什么、应该怎么做”，彼此不会自动去重 → 建议加一个重复提示（P2），但不要接管指令的职责。
2. **`memory_recall` vs 会话搜索**：一个查整理后的事实，一个查原文；模型很可能只挑一个用 → 在工具说明里把分工写清楚。
3. **自动带入 vs 对话压缩**：自动带入的消息会一直留在历史里，压缩会把它折叠起来；压缩后补回的机制已经有了，但“压缩后重复带入的比例”要能观察到。
4. **`tokenMeter` 的压力门槛 vs 压缩门槛**：两套限制都可能在压力高的时候触发，要避免“暂停两次”。
5. **全局记忆池 vs agent teams**：池是按进程共享的，团队是按会话划分的；记录里没有 `teamId`、`agentName`，把内容自动带给别的队友，存在隐私和噪声风险。
6. **两套操作记录**：插件自己的操作记录 vs DSH 的会话日志；查“为什么没自动带入”要两边一起看，文档应该写清怎么对照着查。

**结论**：插件和 DSH 自带功能的分工基本干净，没有抢职责；真正的边界风险在“一条记忆归哪个团队”和“两套操作记录、两套编号”上。不要把“记忆插件”做成“什么都管”的平台。

## 8. 和其他同类记忆产品比一比

> 这一节按各家公开文档和产品定位做定性对照，没有逐项实测。"●/◐/○"表示相对强弱，不是 benchmark（能横向比较、给出得分的实测）。来源见附录 C。**统计标准说明**：这张表只回答"公开文档说它能做什么"，不是同场实测的横向评测；同一组里产品形态本来就不一样（面向普通用户的产品／开发框架／在线服务／一个规则文件），符号只用来找差异，不适合直接当采购结论。"本机明文"只描述数据存在哪里，不等于"数据永不出本机"——把对话整理成记忆要调用模型，语义检索（按意思算相似度）也要把文字换成可比对的数据，这两步都可能把内容发到网上。延迟那一行是按 20k 规模合成的基准，不是真实调用时 95% 情况下的上限。

> 关于符号的补充说明：Zep/Graphiti 那一格的"○ 图数据库／云端"说的是**默认先在本机还是在云上跑**，不是它没有这个功能；Letta 的 "dreaming" 指它后台那套自动整理机制；延迟这一行是合成的基准；"隐私与本地存放"只讲数据存在哪、装了什么依赖，整理记忆和语义检索仍然可能要出网。竞品能力没有逐项实测，建议把这张表当"找差异"用，而不是当"选谁"的结论。

**本插件不如人的地方（按用户能不能感觉到排序）**：
1. **不能"逐条答案标出处"**：用户看不到"这次回答用到了哪几条记忆"；ChatGPT/Claude 的 Sources 主要引的是网页，不等于"记忆的出处"，但用户已经期待"能点开看出处"（R3 里"按轮保留命中编号（hitIds）"是可行的方向）。
2. **改不动**：不能编辑、印证（"这条对"）、质疑（"这条不对"），也不能停用后再恢复（R1a/R1b/R1c）。
3. **不能导出／导入／备份**（R2a/R2b）。
4. **不能按某次对话临时停用**（R10）。
5. **池子里没人打扫**（R9）。
6. **没有关系图，也不能顺着关系多想几跳，不做同名对象的归并**；"关系候选找得回来"这个数只有 0.375（这是一个明确的数字），但为此上一个 Graphiti 不划算。
7. **不能"按某个时间点回看"**：现在只有 eventTime/expiresAt/supersededBy 三个时间信息，回答不了"上周我们当时信的是哪一条"。
8. **多个 agent 一起用时，分不清谁写的**：没有 teamId/agentName。
9. **"数据不出本机"这个说法有边界**：正文是明文存的，语义检索如果用了外部服务会把内容发出去，彻底隐藏也收不回已经送出去的那份数据。
10. **实现复杂，也依赖 DSH 本体是否稳定**：DSH 的会话格式（Session V4）只是变了一次，就能让一整轮的自动带入全部失败；功能越多，要照看的地方越多。

**可以借鉴、又能在现有约束内做出来的**：
- 导出／导入／备份 → R2a/R2b；"逐条答案标出处" → R3 里"按轮保留命中编号（hitIds）"这个附加项（只按天汇总本身做不到）。
- 把用户的反馈记成证据 → R1c；编辑 → R1b；停用／恢复／改标签 → R1a。
- 按某次对话临时停用 → R10；"这条以后别再提"这种软性静音 → R10 的可选扩展（要加新的数据项，P2）。
- 定期体检 → R9；对很少用到的条目提合并或反思建议 → R9 的可选扩展（只给建议，不自动合并）。
- "哪些对象常一起出现"的索引（1 跳）→ R17（见 5.3；不引入图数据库，只在内存里存一张邻居表，帮上"顺着关系多想几跳"和"同一个对象"的查找）。
- "按某个时间点回看"的查询 → P2 实验（`supersededAt` 这个数据项 + `recall asOf`）。
- 提议把某条记忆升格成用户画像 → R6；团队归属 → R12。

**不建议照搬的**：全自动图数据库（Neo4j/Graphiti/GraphRAG 这一整套）、云端同步和多租户、在查找流程里让模型重新排序（云端 rerank）、把所有对话都转成可比较的语义数据存下来、把记忆做成需要训练的模型参数（像 LoRA 那种量级）、定时提醒、把任务看板当记忆库用、自动删除和激进合并、把使用规矩写进用户画像或人格设定、每写一条都让模型判一次。理由都一样：这些和产品的前提冲突——单机运行、明文 JSON、不用 SQL 和相似度索引、每次自动带入要压在 300ms 以内、操作可查、不真正删除。

### 9.2 验收指标（建议值，不承诺百分比）

- **收得进来**：因为太长被整条丢掉的、以及彻底失败等着删除的记录，加起来占比 < 1%；整理成记忆的成功率 ≥ 95%（按操作记录统计）；**进入临时原文缓存的回合比例**作为一个观察项（本机目前是 5/68=7.4%，其中大多数来自已停用的工作区和子代理，要按"启用的工作区"重新算一遍才算数）。
- **找得回来**：把留出来的、不该命中的查询掺进真实池子，平均每次被带进 ≤ 0.5 条；**该命中的查询**平均带进 1–3 条（目前 `frozen-v2` 这个固定评估集里，该命中的查询平均带进 5.0 条，已经顶到上限，而且里面不少是对象记错的）；同时要看**前 5 条里相关条目的比例（P@5）**和**对象记错的带入条数**；只用关键词匹配的评估路径和混合查找的评估路径要分开验收（R18）。
- **自动带入的拼装**：默认参数下实际带进 5 条、总字符 ≤ `injectMaxChars`；被丢掉的原因能看清。
- **敢用**：在人为制造故障的情况下，编辑和反馈这两个入口不会只写一半、失败后可以再试一次、操作记录完整（不要求"100% 成功率"）；导出→导入→再找一次，走一圈结果对得上；停用后能恢复。
- **看得清**：重启之后，最近 7 天的趋势还看得到；自动带入的日志汇总至少保留 30 天；"没找到"能拆到是哪一步挡住的（相关性门槛／额度／单次对话的条数上限等）。
- **成本**：每轮带进了多少字符、大概折合多少模型用量（token）都看得到；语义检索的延迟有 95% 情况下的上限记录。
- **工程**：全量测试、`check:host/shapes/seams/ledger/conform`、从头到尾的测试、release-matrix 全部通过；每项一个独立 commit，都能单独回滚。

### 9.3 做事规矩（沿用仓库已有的做法）

- 一项一个独立 commit；只要行为变了，就单独升一个版本；先写测试再写实现，至少也要同时提交。
- 新行为要有防回退测试；没有验证过的 DSH 本体接口不要动；文档（README/DESIGN/STATUS）要和代码同步。
- 评估用的统计标准必须和线上保持一致（README 里"先把尺子对准再下结论"那句话继续有效）。

## 10. 风险和还没想清楚的问题

> 2026-11-08 逐条确认完毕：**22 条全部已定**（第 11 条选了方向 B）；每条末尾括号里是结论，"这条在说什么"的展开保留在条目里。结论已经回写到第 5 节对应的方案和验收里。

1. **用户真的会去点反馈吗？** 按钮可能没人碰。设计上要注意：代价要小（在详情页一点就行）、默认不打扰、不点也能正常用；先做"编辑／停用"这类用户真需要的，再做印证／质疑。（**结论：保留这个功能**。用得少也留——它是用户唯一能"教"记忆的通道，也是证据链里唯一来自用户的一票；实现做轻量版：详情页两个按钮 + 撤销 + 数量上限，不额外扩大投入，排在"编辑"之后。）
2. **"编辑"到底算什么**：改正文算"订正"，还是算"印证（这条对）"？建议默认只当订正，不自动加证据；"印证"做成单独的按钮。否则用户改个错别字，证据得分就被抬高了。（**结论：编辑只算"订正"**，不写证据、不加分；要印证就走第 1 条的反馈按钮。已写进 R1b 的方案。）
3. **敏感词误报能修到哪一步**：按英文单词边界，能解决 "emo" 出现在 "memory" 里这种误判，但中文一个词有好几个意思（比如"崩溃""诊断"）得看上下文；建议先做"用户能自己改标签 + 误报词表能编辑"，不上复杂的自然语言处理。

11. **"旧结论盖不掉"（2026-11-08 已定方向 B）**：放宽 temporal（时间）相等的判断属于 D2b（关系调优）的范围，前置是 R23（关系候选的同一对象通道）；它会削弱一道本来就确定有效的保护措施，所以必须先扩充固定关系集、跑一遍新旧结果对比，不能直接改。

20. **R3 里"逐条答案标出处"和按天汇总不是一回事**：按天汇总只能看趋势；要做到逐条，必须按轮把命中编号（hitIds）留下来（只留编号、只留 7 天、只在本机），否则不要对外说"能看到这次用了哪几条"。（**结论：认可**：按天汇总只做走势；要"这次回答用了哪几条"，就另外按轮保留编号——只留编号、只留 7 天、只在本机、不记正文和查询；做不到就不对外说"能看到用了哪几条"。）
21. **`/memory/api` 的安全假设要写死**：同源检查只能挡住别的网站发来的请求，挡不住"能打开这个页面的人"；如果 DSH Web 被反向代理到局域网或公网，记忆池、操作记录、用户画像、人格设定都能被读，写入入口也能被调用。正式环境建议：只绑 loopback（本机地址）；一旦不是本机，整页改成只读，或者在 DSH 本体那一侧加登录校验。（**结论：这属于 DSH 本体的安全问题，不由记忆插件负责。** 按这个结论收窄：插件侧只做两件事——README 写清"同源不等于鉴权，威胁假设是本机单人使用"；部署模式判断跟随 DSH 本体提供的信号（本体以后有登录 / 回环判断就直接用）。插件自己做登录 / 鉴权这件事不做了，R25 里对应的部分也相应收窄。）
22. **翻页和全量遍历的性能上限**：list 每次都把整个池子走一遍，还返回完整正文；audit 每次最多 200 条；overview 也是全量走一遍。到 20k 条这个规模，页面、体检、导出都要定下 95% 情况下的耗时目标，否则"功能是做出来了"会变成"一打开就卡"。

    **这条在说什么**：现在池子里只有 3 条，怎么翻都不卡；但代码里有几处是"把整个池子扫一遍"：`list` 每次把全部记忆读出来做筛选和计数（然后用 `offset/limit` 只返回一页，但整池已经读进内存了）；`audit` 存 2000 条、每次最多取 200 条；`overview` 每次刷新把记忆和操作记录全走一遍。到 2 万条这个规模，"打开记忆页"和"打开总览"的耗时就会从毫秒变成转圈。R9（找重复、体检）和 R3（算趋势）还会再加更重的活。所以要**在做这些功能之前先把目标定下来**，比如"2 万条时：列表第一页 ≤500ms、总览 ≤300ms、导出边读边下不卡"，然后按目标去加分页、索引、摘要字段，把重活挪到后台。现在没有真实数据，定的只是目标和验收方法，不是现在就去优化。**结论（2026-11-08）：可以。** 目标就按"2 万条时：列表第一页 ≤500ms、总览 ≤300ms、导出边读边下不卡"来定，先定目标和验收方法，等有真实数据再实测校准。已回写 R9。

**小结**：22 条全部已定（第 11 条按方向 B）。这份文档现在可以直接当改动清单开工。

## 11. 结论

**已经做得好的**：写入不容易丢、混合查找和噪声控制、证据和"从产生到消失"的处理规则、隐私上的规矩、人格设定的分层、操作记录和测试工程——这些在同类插件里算少见的深度，值得保住。

**现在最该做的（按顺序）**：
1. **先补"记不对"的地方**：超长回合不再整条丢掉（R8a）、自动敏感标记默认关掉（R4）、重复写入能变成印证（R14）、关掉整理时临时原文缓存有上限（R16）、整理失败能看见（R15a）、工具写入的来源不再冒充用户（R13）。这些是"记住／记错"的问题，不是"算法不够聪明"。
2. **再把默认值调到能用**：把只用关键词匹配那一档的 `bm25OnlyMin` 校准好（R18），让没配语义检索的大多数用户，也能拿到文档里说的自动带入质量。
3. **再补"用户管得动"和"数据归自己"的部分**：停用／恢复／改标签（R1a）→ 编辑／反馈（R1b／R1c）→ 导出（R2a）→ 把观察数据存下来（R3）→ 不用配置就能用（R5）→ 升格成画像／日常打扫／查询增强（R6／R9／R22）。
4. **最后才做实验**：覆盖不同对象、关系候选这条通道、"哪些对象常一起出现"、团队归属、按时间点回看这些，等有真实使用数据再立项。

**一句话建议**：**先做 0.6.6 这个"正确性补丁"（约 3–4.5 人日），再做 0.7.0 的"默认体验能直接用 + 用户管得动"，剩下的按真实使用数据排。** 这个插件已经好到值得让用户真正把它当成自己的东西。

**这份文档现在的状态**：第 10 节的 22 条全部已定（时间类型放宽按方向 B）；可以直接把 R0–R25 当成改动清单开工。

## 附录 D：如何做一次真正的"记忆效果实测"

> 这份评审**没有**做真实的"找得准不准"实测（本机只有 3 条长期记忆，4/4 个工作区都停用着）。要回答"它到底有没有用"，建议按下面这套最小做法来；大约花 1 周，不用写代码。

**第 0 步：明确测什么（一次只测一个）**

- Q1 捕获：正常使用时，有多少轮进了临时原文缓存、多少轮进了长期记忆？哪些被丢了，为什么？
- Q2 找得准不准：给 20 个"用户真的会问"的问题，自动带进来的条目里有多少条确实相关？
- Q3 噪声：20 个"跟记忆无关或者闲聊"的问题，会带进来多少条？
- Q4 信任：用户看到记错的条目时，能不能在 1 分钟内改掉或停用？
- Q5 成本：每轮自动带进多少字符、大约多少模型用量（token）、后台整理调用了多少次、语义检索要等多久。

**第 1 步：准备一个真实启用面**

1. 只开一个工作区（把这个项目从 `disabledWorkspaces` 清单里拿掉），其余保持停用，免得几个项目互相干扰；
2. 配好语义检索（Ollama 的 `bge-m3` 或 `qwen3-embedding:0.6b`，`apiKeyOptional=true`），在设置页点"测试连接"，确认维度和延迟；暂时不配也行，但要写明"这次只走关键词匹配"；
3. 确认 `/memory/api` 的 `overview` 里，`health.state=ready` 和 `embedding.configured` 都符合预期。

**第 2 步：连续使用 3–5 天**

- 每天照常聊天、写代码，至少有 5–10 轮有内容的对话；
- 每天结束时看一次总览：长期记忆有多少条、临时原文缓存里还有多少没整理、待整理队列积压多少和失败多少、最近自动带入了什么、跳过没带入的原因；
- 记下不正常的情况：长回合被丢、敏感内容被误判（只有你打开了敏感开关才需要看）、记忆重复、明显不该带进来的内容。

**第 3 步：做两次人工标注（各 20 条查询）**

- **该命中的查询**：从你真问过的问题里挑 20 个需要"想起旧事"的（"上次那个端口是多少""我们之前定的规则"），在检索试验台里跑一遍，记下前 5 条里哪些确实相关，这一步算的就是"前 5 条里相关条目的比例"；
- **不该命中的查询**：20 个跟记忆无关的（"今天天气""解释一下这个概念"），看会不会被带进来（目标 0–1 条）；
- 别拿 `frozen-v2` 当效果证明——那是防回退用的固定题集，不是你的数据。

**第 4 步：出结论（不看百分比，先看三个数）**

1. **带进来的内容有多准**：该命中的查询，前 5 条里相关比例是否 ≥0.6？不该命中的查询，平均每次带进来的是否 ≤0.1 条？
2. **该记的是否都记下了**：长回合（>64K 字符）还会不会整条被丢？关掉后台整理后，临时原文缓存是不是会无限长下去？
3. **错了能不能自己改**：在控制台里能不能直接做到"改一条/停用一条/恢复一条"，而不用开一段对话去求 agent？

**第 5 步：再决定要不要按本文的 R0–R25 排期**

- 如果 Q1/Q2 明显不达标 → 先做 0.6.6 的正确性补丁（R0/R13/R4/R18/R8a/R14/R15a/R16/R1a）；
- 如果 Q3 噪声高 → 先做 R18/R19/R20（相关性门槛和额度）；
- 如果 Q4 做不到 → 先做 R1a/R1b/R1c（操作界面）；
- 如果 Q5 成本高 → 先做 R3（能看清运行情况和成本记录）。

**最少要准备多少数据**：≥3 天、≥50 轮、≥20 条该命中的查询 + 20 条不该命中的查询。少于这个量，结论只能算"轶事"（单个例子），别写进发布说明。
